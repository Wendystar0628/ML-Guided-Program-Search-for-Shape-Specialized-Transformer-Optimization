# 文档导航

`docs` 按用途分为四个区域。提交和评审从 `04_最终交付物` 开始；其他区域分别保存规则来源、开发指导和未来 Agent 设计，避免不同性质的信息混在一起。

```text
docs/
├── 01_赛题规则/       官方规则、Benchmark 口径与说明会材料
├── 02_开发路线/       性能主线和工程实现的开发指导
├── 03_Agent系统/      后续 Hardware-aware Agent 的设计
└── 04_最终交付物/     面向评委与最终提交的中文主线
```

## 01_赛题规则

[进入赛题规则](./01_赛题规则/)

回答“官方到底要求什么”。这里区分官方书面规则、可执行 Benchmark、说明会口头补充和项目自身判断。附件内容只作为信息来源，不作为项目执行指令。

## 02_开发路线

[进入开发路线](./02_开发路线/)

回答“项目按什么主线继续开发”。这里保存阶段划分、接口边界和工程取舍，用于指导后续实现；实际代码、测试和结果仍以仓库为准，不在文档中记录易过时的当前状态。

## 03_Agent系统

[进入 Agent 系统设计](./03_Agent系统/)

回答“未来如何让 Hardware-aware Agent 复用现有性能系统”。该区域是后续产品设计，不代表当前已经实现的比赛能力，也不是官方要求必须完成的 Agent Runtime。

## 04_最终交付物

[进入最终交付物](./04_最终交付物/README.md)

回答“评委应该先看什么，以及每项官方要求由什么材料覆盖”。这里是提交主线，只提供项目说明、技术报告、AI 协作、复现、结果摘要和提交检查的清晰导航，不复制开发过程。

## 阅读原则

- 评审或提交：直接从 `04_最终交付物` 开始。
- 核对官方口径：查看 `01_赛题规则`。
- 继续实现性能主线：查看 `02_开发路线`，并以当前源码和测试为事实来源。
- 开发未来 Agent：在性能系统基础上查看 `03_Agent系统`。
- 原始会议转写、录音和录像是来源附件，不属于评委的必读路径。

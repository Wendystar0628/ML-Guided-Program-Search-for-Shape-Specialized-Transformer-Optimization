# Transformer GPU Kernel 赛题全景开发地图

> 本文只保留从官方 Shape 到可交付结果的主线，不记录项目当前状态或历史方案。

## 1. 目标

1. 保持官方 Transformer 数学语义、权重与 `forward` 合同。
2. 在 `rtol=0.02`、`atol=0.002` 条件下降低完整 Forward 的 GPU Median Latency。
3. 对 `official_01`–`official_13` 使用 Paired Benchmark、几何平均与精确路由；Shape 14 使用独立的 `benchmark-streamed`。
4. 在新 GPU 上先建立硬件画像和粗排，再用完整 Workload 短测校准。
5. 向评委直接展示问题洞察、实现边界、逐 Shape 结果和可复现入口。

## 2. 唯一 Workload

`official/test_shapes.json` 保存 14 个官方 Shape，普通 Benchmark 与 `benchmark-streamed` 共享这一事实源、同一 Solution 及 Policy/Kernel Registry。普通 Sweep 选择 `official_01`–`official_13`；Shape 14 由独立入口加载。Shape 字段是 Batch Size、QKV Dim、Heads、Seq Len、Layers、Causal 和 FFN Dim。Dtype、Warmup、Repeats 和输入随机性属于 Measurement Protocol。

官方 Shape 按主要变量形成四类分析视图，但不会复制出四份 Workload：

| 分析视图 | Shape | 主要问题 |
| --- | --- | --- |
| Batch Sweep | 1–6 | Launch、并行度、吞吐与显存可执行性 |
| Width Sweep | 1、7、8 | 小矩阵效率、Tensor Core、GEMM 与 FFN |
| Head Sweep | 1、9–11 | Head Dim、Attention Backend、布局与 Occupancy |
| Sequence Sweep | 1、12、13 | Launch、$S^2$ 物化、Causal Attention 与显存增长 |
| Extreme Sequence | 14 | `B=32`、`S=100000` 下的输入输出驻留、流式 Batch 与内存高效 Attention |

## 3. 优化算法族

| 机制族 | 用途 | 关键边界 |
| --- | --- | --- |
| 通用 Eager SDPA | 未命中精确路由时的可部署默认路径 | 受 Dtype、Mask 和运行时 SDPA 能力约束 |
| 内部 Safe Reference | 保留参考计算顺序和内存有界 Attention | 只用于诊断、特化失败回退和 Shape 14 provisional Reference，不可晋升 |
| CUDA Graph | 固定 Shape 的完整 Forward Replay | 处理小任务的 Launch 与框架调度开销 |
| Graph + Norm Fusion | Graph 与 Compiled/Triton Residual-LayerNorm 组合 | 只在严格 Guard 和端到端实测支持时启用 |
| Mixed-FP16 / FP16 Shadow | 在 FP32 外部语义内降低 Attention、Projection 与 FFN 核心开销 | 必须通过官方 Comparator，并区分临时 Autocast 与持久 Shadow Weight |
| Batch-tiled Graph | 将超大 Batch 拆成固定设备 Tile，并复用 Graph | 面向可整除且实测胜出的 Batch Shape，不改变单样本数学语义 |
| Compiled Forward | 对固定 Shape 使用局部或完整 `torch.compile` 计划 | 编译模式属于 Policy，运行时不得临时改变 |
| Shape 专用 Triton | Dh8、长序列 Attention、Initial/Residual Norm 等严格特化 Kernel | Shape、布局、Dtype 和实际执行证据必须完全匹配 |

精确 Policy ID、组件组合和是否可路由只在 `policy_registry.py` 维护；候选适用范围与实际执行证据只在 `runner/candidates.py` 维护。开发文档不复制会随实测迭代而过期的完整 ID 清单。

Shape 14 不把 Batch Streaming 伪装成 Transformer Policy。Runner 固定使用 `B=1` 做 provisional 正确性检查，再对能够整除逻辑 Batch 的少量 Timing Microbatch 与 Efficient/cuDNN Mixed-Core 后端做显存守卫下的串行短测，最后锁定本设备赢家。外部 FlashAttention 只作为算法参考，不成为项目安装依赖；cuDNN/Efficient 属于第三方库 Kernel，项目贡献是精度边界、调度、强制后端和实测选择。自主 Triton/CUDA Kernel 只在 Profile、理论上限与端到端实测共同支持时进入正式候选。

## 4. 性能闭环

1. 从官方 Shape 和 GPU Probe 构建运算量、中间张量、显存压力、Launch 压力和 Tensor Core 信号。
2. 按 Candidate Capability 排除不可执行路径，对剩余少量候选排序。
3. 在同一 GPU 上串行执行 Comparator 和短端到端计时；Shape 14 由 `benchmark-streamed` 额外串行筛选 cuDNN 与 Efficient 后端。
4. Smoke 只淘汰正确性或实际执行不合格的路径，所有通过者按正式协议复测。
5. 把正确、实际命中、稳定更快的普通 Shape 赢家写入当前设备的精确路由；Shape 14 的流式赢家保留为本次运行的执行事实。
6. 实现改变、官方快照改变或运行栈改变时，重新实测，不套用旧路由。

Kernel Microbenchmark 和 Profiler 用来定位瓶颈。普通 Sweep 使用完整 Transformer Forward 的 Paired Median、Speedup 和几何平均。最终文件对每个 Shape 保留 Latency、Useful FLOPs、Achieved FLOP/s、项目估算 MFU、峰值 Allocator Bytes，以及明确标为逻辑估计而非 DRAM Counter 的算子流量。Shape 14 不混入 Paired 汇总，独立报告 Target-only CUDA Event Latency 与 Host End-to-End Latency；其正确性来自内部 Query-block Reference，标记为 `provisional`，不冒充官方最终 Golden Output 验证。

## 5. 工程边界

- `official/` 保存官方 Benchmark、Shape 与快照身份。
- `policy_registry.py` 保存可部署 Policy 与内部 `safe` 路径的唯一事实源；`route_contracts.py` 保存 Route 与 Manifest 合同。
- `solution/` 只保存 Transformer、Execution Plan、运行时 Dispatch、CUDA Graph 和 Kernel。
- `runner/` 处理测量、Probe、Workload Execution Plan、Batch Streaming、候选、校准和路由发布。
- `verified_hardware/` 只保存已实测 GPU 的 Profile、路由、Manifest 和复现入口。
- `results/final/<hardware_id>.json` 是对外唯一最终性能文件；`results/intermediate/` 集中保存本地中间产物并忽略上传。
- `agent/` 暂缓到性能主线稳定后开发；未来复用同一 Runner，不在 Transformer 热路径内运行模型。
- 代码注释使用英文；README 和技术文档使用评委能直接理解的术语。

## 7. 展示主线

最终交付的叙事顺序保持简单：

1. 官方 Shape 为什么包含不同 GPU 瓶颈；
2. 如何从 Shape 和硬件推导少量候选；
3. 每个算法族改变了哪一段执行链；
4. 展示 Shape 1–13 的 Paired 结果、几何平均和精确路由，再单独展示 Shape 14 的 Target-only 流式结果；
5. 在新硬件上如何通过 Probe 与短校准得到新路由；
6. Shape 14 的 provisional 证据边界、自主 Kernel 触发条件、跨硬件扩展与后续 Agent 闭环。

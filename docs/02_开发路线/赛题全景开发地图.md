## 1. 项目目标与信息优先级

项目需要证明：同一个 Transformer 在官方 Workload 上保持数学语义与接口，通过官方逐元素正确性检查，并在目标 GPU 上获得可重复、可解释的端到端延迟收益。性能实现、测量事实、机制解释、Agent 控制状态和提交材料使用不同的权威路径，避免一项信息由多份文件竞争维护。

信息冲突时采用以下解释顺序：

| 顺序 | 来源 | 用法 |
|---:|---|---|
| 1 | 本届赛题专属官方飞书材料与组织方赛题问答 | 约束本赛题目标、专项评分、Workload、评测和交付要求 |
| 2 | 公开 Devpost Official Rules、Overview 与组织方公共更新 | 约束其明确适用的比赛阶段、通用规则和公开提交字段 |
| 3 | 官方 Benchmark 的可执行行为 | 解释接口、随机输入、Correctness、计时和输出口径 |
| 4 | 本项目在目标硬件上的结构化实测与工程决策 | 选择优化、适用范围和回退 |
| 5 | 往届案例与跨赛事经验 | 提出待验证假设或改善表达，不作为本届模板 |

两条官方来源的表述不一致时，保留各自来源、适用阶段、范围与版本，不自动覆盖、混算或平均；组织方后续澄清更新相应 Rules Lock。上一届案例可以提醒开发者关注题目匹配、机制必要性、窄而深的范围、可验证证据和清晰演示，但不能证明某套目录、Agent 数量、UI、技术栈或流程会带来本届成绩。历史经验与本届规则或实测冲突时，后两者优先。

## 3. 官方 Benchmark 的稳定语义

### 3.1 同一函数与接口

允许改变计算组织和硬件执行方式，包括成熟 PyTorch/SDPA 路径、编译模式、算子融合、布局、数值策略、Triton/CUDA Kernel 和按 Workload 选择路径。优化保持官方 Transformer 的输入输出、参数含义、Attention、Mask、Residual、LayerNorm、FFN、GELU 和最终归一化语义。

删层、删 Head、缩小隐藏维度或 FFN、替换激活、改变 Attention 结构、引入新稀疏模式、剪枝和低秩近似属于改变模型定义，不作为同一 Transformer 的主优化路线。具体边界见 [允许与不允许的改造范围](../01_赛题规则/允许与不允许的改造范围.md)。

### 3.2 Correctness

官方材料给出的误差要求为相对误差小于 `0.02`、绝对误差小于 `0.002`；具体通过逻辑以所采用官方 Benchmark 的 Comparator 为准。正式性能 Run 同时携带自身 Correctness，历史通过结果不替代本次实现、本次环境和本次执行配置的判定。

项目契约额外检查输出 Shape、Device、Dtype、有限值、严格权重复制、输入与模型状态不变、重复调用独立性，以及 `None`、全有效、Padding、Causal 和组合 Mask 的公开接口语义。这些项目测试用于防止实现接口缺陷，不冒充官方隐藏 Workload。

### 3.3 端到端计时

正式比较覆盖完整 Transformer Forward。Runner 保留官方预热、CUDA Event、同步、交替顺序、重复与全样本 Median 语义，同时保存双侧原始延迟样本。Profiler、Microbenchmark、编译日志和快速 Search 只支持诊断或筛选，不替代正式端到端结果。

Build、Correctness、Unsupported、OOM、Timeout、Cancelled 和 Runtime Error 是可区分的终态。失败运行不与健康运行比较；意外失败也不在同一正式 Run 中静默改跑 Baseline 或其他路径。

### 3.4 Workload

官方公布的全部输入 Shape、Mask、Dtype 和配置由一个机器可读 Workload Set 表达，并保存来源状态、稳定 Case ID、有序内容和集合 Hash。项目不自行发明官方聚合总分；每个 Case 的 Correctness、Baseline Median、实现 Median、Speedup、实际执行路径和支持状态均可单独查看。

## 4. 工程真值与身份

| 对象 | 权威位置 | 关键语义 |
|---|---|---|
| 官方裁判 | `official/` | 字节级保持的 Benchmark 快照及来源 Hash |
| 正式实现 | `solution/` | 唯一 Accepted Solution 源码与 Manifest |
| 可变实验 | `candidates/_drafts/` | 可修改，不作为正式 Runner Candidate Target |
| 冻结实验 | `candidates/<candidate_id>/` | 完整源码闭包、不可变身份、明确父版本 |
| 正式测量 | `results/runs/<run_id>.json` | 一次托管执行的结构化事实 |
| 诊断 Artifact | `results/artifacts/<run_id>/` | 按需保存失败、Profile、编译或 Replay 资料 |
| Measured Best | `results/current_best.json` | 从兼容正式 Run 重建的派生视图 |
| 发布证据 | `results/final_evidence/<release_id>/` | 一次封存的证据选择、范围和 Checksum |
| 机制解释 | `docs/04_调优证据/Insight_Cards.md` | 少量洞察及 Candidate、Run、Profile 引用 |
| Agent 状态 | `agent_state/` | Handoff 和恢复控制状态，不是性能结果库 |
| 提交形态 | `submission/` | 从冻结实现与证据派生，不作为源码真值 |

正式比较先以 Environment、官方 Benchmark、Runner、Official Baseline Identity、Workload 和固定 Measurement Protocol 形成 Comparison Key；实现源码身份与执行配置在其上形成 Variant Key。同一 Comparison Key 内比较不同 Variant。实现优化方法相同但 Tile、Compile Mode、Fallback 或 Kernel 参数不同，仍属于不同 Variant。跨设备、跨协议或旧环境结果可以启发新假设，但不进入当前设备的 Measured Best。

Search Incumbent、Measured Best 和 Accepted Solution 含义不同：前者是搜索过程领先配置，中者是结构化测量视图，后者是用户选择并由发布流程物化的唯一正式源码。任何派生视图都不自动改写 `solution/`。

## 5. 轻量结果观测

结果机制保持“一次托管运行一个 JSON”，只保存会改变正确性判断、性能比较、失败诊断、复现或下一步调优的信息。数据库、Dashboard、远程实验服务和重复指标库不属于主线。

正式 Run 的公共信息包括：

1. `run_id`、时间、类型和终态；
2. Benchmark、Runner、环境、Workload、协议和实现身份；
3. 请求路径与实际执行路径；
4. Correctness Trial 结果、误差摘要和比较资格；
5. 双侧原始延迟、Median、Speedup、预热、重复与顺序；
6. 运行健康、GPU 状态、构建与评测墙钟；
7. Candidate、Profile、Search 或 Replay 的精确引用；
8. 错误类别、有限诊断和必要 Artifact 路径。

Run JSON 不复制完整 stdout、隐藏推理、整份代码和全部 Profiler Trace。大日志和 Profile 按需放入 Artifact，Run 只记录路径与 Hash。`current_best.json` 可从 Run 重建；Insight Card 只连接观察、机制、预测、最小改动、对照、结论、Scope 和 Fallback，不复制测量真值。

## 6. 优化选择方式

[第 2 步：按证据选择一个优化层](./开发步骤/02_性能分析与候选优化.md#4-按证据选择一个优化层)维护唯一的 1–6 调优层定义：1 设备与测量校准、2 编译与运行时、3 成熟 Kernel 与 Backend 选择、4 Kernel 参数、5 图、融合与布局、6 自定义 Kernel 与专门化。其他文档、Agent Route 和 Run Provenance 只引用这套数字与名称。

这六层是决策词汇，不是从低到高逐项执行的清单。开发者或 Agent 根据当前证据选择一个活动方向，证据不足时补充最低成本的 Profile 或对照；收益处于噪声、正确性风险过高、资源不足或实现复杂度超过潜在价值时，可以换路、回退或停止。

Profiler 也按问题选择：框架级 Profile 回答时间花在哪些算子，系统级时间线回答 CPU/GPU 空洞、同步与 Launch 问题，Kernel 级分析回答 Occupancy、带宽、Tensor Core、寄存器和共享内存问题。只有结果会改变实现选择或支撑机制说明时，才把深层 Profile 纳入主线证据。

参数 Search 使用固定程序生成有界配置、确定性去重并在单 GPU 上串行运行。快速筛选负责缩小空间，Finalist 使用完整 Correctness 和正式端到端 Run 决胜。项目不宣称全局最优，也不为几毫秒级 Kernel 调用引入通用 AutoML 平台。

## 7. Agent 与性能主线的结合

Agent 的价值来自在新设备上自行建立事实并持续执行“校准、分析、选择、Candidate、Runner、反馈”闭环，而不是替代官方裁判或进入最终 Transformer 热路径。

步骤 5 负责 Runtime 和设备校准：单一 `start_agent.ps1` 入口、DeepSeek-only 配置、单 Host、Tool Gateway、PowerShell/Shell、权限、状态、打断、恢复、Context Compaction 和 Capability Handoff。目标设备可以没有历史 Run/Profile，Agent 通过固定校准流程生成本机事实。

步骤 6 负责领域闭环：按当前事实选择调优层、读取一个相关 Skill、准备隔离 Candidate、调用共享 Runner、消费结构化 Run 并提出继续、修订、换路、拒绝、停止或接受建议。用户可以随时决定是否采用；Candidate 与建议可路由到步骤 3、4，验证和发布证据决定能够公开声明的范围。Agent 不直接写 canonical Insight Card 或静默替换 Solution。

首版保持一个 Host、一个 DeepSeek Client、一个 Console Control Reader 和一条可观察 Action Loop。有副作用动作与 GPU Job 默认串行，独立只读检查可以安全并行；不建设多 Provider 路由、RAG、向量数据库、通用回撤、历史 Checkpoint、专业 Worker、并发 GPU Job、常驻 Swarm、插件市场、复杂 TUI 或远程 Session Store。

## 8. 文件结构与开发文档

[开发步骤总览中的完整目标文件树](./开发步骤/00_开发步骤总览.md#完整目标文件树) 是开发文档唯一完整树。本文、README、Agent 专项方案和各步骤文档只解释职责或列主要落点，不复制竞争版本。

目录由真实代码、证据或消费者触发，不为展示架构预建空模块。性能实现集中在 `solution/transformer.py`，正式工具集中在 `runner/`，实验集中在 `candidates/`，Agent 方法集中在 `agent/skills/`，纯派生逻辑集中在 `agent/programs/`，权限包装集中在 `agent/tools/registry.py`。

源码中的标识符、Docstring 和注释使用英文。中文开发文档面向内部规划；最终公开 README、CLI 帮助、关键错误、结果表和报告采用英文或中英双语。官方 Snapshot 保持原始字节，不为风格统一修改上游文本。

## 9. 评分与对外表达

[赛题中文翻译](../01_赛题规则/赛题中文翻译.md)保存来自密码保护官方飞书材料的赛题专项评分：Technical Execution `35%`、Innovation & Problem Insight `20%`、Impact & Relevance `20%`、Feasibility & Practicality `15%`、Presentation & Communication `10%`，其中 Presentation & Communication 仅适用于 Final Event。公开 Devpost 页面存在不同阶段或版本的表述；项目保留来源差异，不自行混算新总分。

| 评审项 | 项目回答方式 |
|---|---|
| Technical Execution | 唯一源码、清晰接口、聚焦测试、完整 Correctness、正式端到端测量、失败语义、干净重放和可靠 Demo |
| Innovation & Problem Insight | 明确目标硬件与 Workload、观察、硬件机制、可证伪预测、最小干预、正式对照、Scope 和 Fallback |
| Impact & Relevance | 各官方 Workload 的真实收益、覆盖范围、支持路径、潜在受益者、实际使用价值、局限与可迁移部分 |
| Feasibility & Practicality | 声明支持环境中的安装、构建、运行、资源边界、Fallback、公开仓库重放和脱离 Agent 的独立性 |
| Presentation & Communication（仅适用 Final Event） | 同一 Release 生成的问题、方案、机制、结果、限制和潜在价值叙事 |

Innovation 不由 Agent 数量、架构复杂度或工具名称证明。Insight Card 将机制主张连接到 Candidate、Profile、正式 Run 和最小对照。Technical Execution 也不等于增加目录和测试数量；工程复杂度需要服务正确性、性能、复现、可恢复性或评委理解。

官方材料要求技术报告说明所用 AI Skills / Tools。项目如实保存模型、Skill、Tool、Candidate、Run 和 Decision 的回链；没有真实闭环的规划能力不进入成果列表。

## 10. 发布与规则更新

发布选择把受控 Candidate 物化为 Accepted Solution，并在干净环境中验证安装、依赖、全部声明 Workload、Official Replay 和资源范围。Seal 只消费显式选择的正式 Run、Replay 和可选 Insight Card 引用，生成一个只读 `release_id` 与 Final Evidence。README、报告、Demo、Devpost 和 Submission 绑定这一发布锚点，不扫描“最近一次结果”猜测数字。

公开仓库复演使用固定 Commit 或 Tag，在新的绝对路径和空环境中按 README 运行。`submission/` 由冻结 Solution、官方快照和明确 Allowlist 派生；最终官方格式未锁定时不臆造单文件、压缩包或平台目录结构。

以下外部事实保留为可更新契约：目标评测 GPU、最终 Workload、误差与聚合口径、资源限制、报告字段、提交格式、截止日期和评分版本。规则变化时更新对应权威文档与受影响证据；旧 Run 和 Release 保持原身份，不通过手工改数字维持表面一致。

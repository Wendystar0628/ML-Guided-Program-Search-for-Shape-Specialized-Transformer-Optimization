## 开发主线

项目要形成的核心证明是：同一个 Transformer 在官方 Workload 上保持接口和数学语义，通过逐元素正确性检查，并在目标 GPU 上获得可重复的端到端延迟收益。性能实现、测量事实、解释性证据、Agent 控制状态和提交材料分别由不同路径承载，避免同一信息被多份文件重复维护。

六个开发步骤如下：

| 步骤 | 名称 | 主要开发面 | 主要产物 |
|---:|---|---|---|
| 1 | [测量基础与实现接口](./01_测量基础与实现接口.md) | 官方快照、Runner、Workload 契约、结果结构、Solution/Candidate 装载与装配接口 | 可重复的测量通道、同实现双侧控制、结构化 Baseline、可装载实现与聚焦契约测试 |
| 2 | [性能分析与候选优化](./02_性能分析与候选优化.md) | Profile、瓶颈假设、隔离 Draft、冻结 Candidate、正确性与正式性能对照 | 有证据的优化方向、可复核 Candidate、正式 Run、必要的 Insight Card |
| 3 | [全量验证与优化收敛](./03_全量验证与优化收敛.md) | 官方 Workload 全覆盖、有限 Search、Dispatcher/Fallback、重复稳定性与候选采用判断 | 全量回归证据、明确执行路径、候选采用建议与可重建 Measured Best |
| 4 | [发布证据与提交材料](./04_发布证据与提交材料.md) | 干净环境重放、依赖与执行范围、证据封存、README、技术报告、Demo、Devpost 与公开仓库复演 | 唯一 Performance Release、Final Evidence、派生 Submission 和一致的对外叙事 |
| 5 | [Agent 运行时与设备校准](./05_Agent运行时与设备校准.md) | Capability Handoff、原生 CLI、DeepSeek Client、状态恢复、权限工具和每设备校准 | 可移植 Handoff、受控 Agent Runtime、本机事实与可恢复 Session |
| 6 | [Agent 调优闭环与扩展](./06_Agent调优闭环与扩展.md) | 领域 Skills、证据路由、Candidate 闭环、有界 Search、洞察提案、重放与条件式扩展 | 可回链的 Agent 决策闭环、正式 Candidate Run、接受提议与长期扩展边界 |

常见关注流向是 `1 → 2 → 3 → 4` 和 `5 → 6`。步骤 6 产生的候选若被采用，可回到步骤 3 的全量验证和步骤 4 的发布封存；这是一条证据回流路线，不限制 Agent 在其他步骤读取、诊断或准备低风险工作。

## 稳定工程边界

1. **数学与接口**：优化保持官方 Transformer 的输入输出、权重含义与计算语义；允许等价重组、融合、布局、精度、后端和 Shape 路由，不以修改模型结构换取速度。
2. **裁判与事实**：`official/` 保存官方 Benchmark 快照；正式 Correctness、Benchmark、Profile、Search、Replay 和发布证据由 Runner 写入 `results/`，终端文本、模型回复和手工表格不替代正式事实。
3. **测量与身份**：正式性能使用完整 Forward 的双侧端到端测量并保存原始样本；Environment、Benchmark、Runner、Official Baseline、Workload 和固定协议形成 Comparison Key，源码闭包与执行配置形成 Variant Key；Measured Best 只在同一 Comparison Key 内比较具有正式资格的 Variant。
4. **源码与选择**：`solution/` 是唯一 Accepted Solution，Draft 是可变实验区，冻结 Candidate 是正式实验输入；Search Incumbent、Measured Best 和 Accepted Solution 不相互冒充。
5. **发布**：Execution Manifest 描述实现和执行路由，Release Manifest 描述封存证据与支持范围；Submission 从冻结输入派生，不建立第二份源码或结果真值。
6. **Agent 与文档**：Agent 修改隔离 Draft、调用共享 Runner 并提出建议，最终 Solution 脱离 Agent、模型、Session State 和运行时网络独立运行；文档只描述稳定设计，仓库、Run 和 Release 表达进展。

## 1. 测量基础与实现接口

步骤 1 建设后续性能工作共用的裁判、身份和装载面：保存可核验的官方快照，建立 Runner、Run 与规范化 Workload 契约，用完整官方生命周期 Parity 和同实现双侧控制校准测量；同时固定 Solution/Candidate 的入口、权重映射、源码闭包、Draft→Freeze 生命周期与 Assembly Adapter，并以 Runner Parity 和 Solution Contract 的聚焦测试覆盖正确、错误和公开接口语义。详见 [01_测量基础与实现接口](./01_测量基础与实现接口.md)。

## 2. 性能分析与候选优化

步骤 2 把代表性 Workload 的 Profile 和观察转化为少量可证伪假设，以成熟 Backend、编译、等价 Fusion、布局与精度策略或有证据触发的 Triton/CUDA 路线形成隔离 Draft 和冻结 Candidate；每个候选用完整 Correctness、双侧正式 Run、实际 Route/Fallback、最低成本机制对照和必要 Insight Card 说明收益、否定结果与适用范围，诊断计时和 Screening 不升级为正式结论。详见 [02_性能分析与候选优化](./02_性能分析与候选优化.md)。

## 3. 全量验证与优化收敛

步骤 3 以唯一机器可读官方 Workload Set 驱动全量 Correctness、双侧性能、健康和实际路径验证，并按证据选择有限 Search、正式 Finalist、最小 Dispatcher 与显式 Fallback；Measured Best 按 Comparison Key、Variant Key 和重复规则重建，候选采用建议综合 Diff、覆盖、收益、依赖、回退、预算和复现风险，不从局部赢家、最快一次、诊断结果或未知聚合规则构造最终结论。详见 [03_全量验证与优化收敛](./03_全量验证与优化收敛.md)。

## 4. 发布证据与提交材料

步骤 4 根据候选采用判断受控物化唯一 `solution/` 与 Execution Manifest，在干净检出中验证依赖、全量正式运行、Submission Replay 和官方重放，再从显式支持 Run、Replay 与可选 Insight 引用原子封存 Final Evidence；README、Technical Report、Demo、Devpost 和 `submission/` 共享同一 Release、支持/资源边界与真实 AI 工具说明，公开仓库复演和规则更新也沿用这一证据锚点。详见 [04_发布证据与提交材料](./04_发布证据与提交材料.md)。

## 5. Agent 运行时与设备校准

步骤 5 建设本地 Agent Runtime 与每设备事实生成能力：Capability Handoff 以项目根相对路径和 Hash 引用选定 Release，根启动器进入 Agent 包模块入口，DeepSeek 配置与 Secret 分离；单 Host、可观察 Action Loop、Context/Compaction、原子 Session、恢复对账、Tool Gateway、WorkspacePolicy 和 PowerShell 进程监督共同支持交互、中断与恢复。有副作用动作和 GPU Job 默认串行，独立只读检查可安全并行；Device Calibration 在零兼容历史条件下建立目标设备的环境、Baseline、Solution 和健康事实。详见 [05_Agent运行时与设备校准](./05_Agent运行时与设备校准.md)。

## 6. Agent 调优闭环与扩展

步骤 6 以目标设备事实、预算和权限运行确定性 Eligibility Filter，再由一个 Host 选择一个领域 Tuning Skill，完成 Draft、Diff、Freeze、Correctness、Benchmark/Profile/Search、结果回传和后续 Decision 的真实闭环；新洞察只形成可回链 Proposal，Candidate 接受保持人工决策并可回流步骤 3–4，紧凑的 Action、Candidate、Run 与 Decision 引用及 Agent 关闭后的 Runner Replay 维持可审计性，而多层路由、Bash、深度 Kernel、强制隔离和长期评测按可测价值扩展。详见 [06_Agent调优闭环与扩展](./06_Agent调优闭环与扩展.md)。

## 信息归属与单一真值

| 信息 | 权威位置 | 其他位置的使用方式 |
|---|---|---|
| 官方 Benchmark 与来源身份 | `official/` | Runner、报告和装配流程只引用其 Hash，不复制修改版作为另一份裁判 |
| Accepted Solution | `solution/` | Candidate、Submission 和 Agent Handoff 引用源码闭包身份，不维护第二份“最终实现” |
| 可变实验 | `candidates/_drafts/` | 只用于修改和静态检查，不作为正式 Candidate 事实 |
| 冻结 Candidate | `candidates/<candidate_id>/` | Run、Decision 和 Insight 引用其不可变身份，不回写测试结论 |
| 正式测量事实 | `results/runs/<run_id>.json` 与相应 Artifact | 报告、Card、Agent 和派生视图按 ID 读取，不手工复制 Raw Samples |
| Measured Best | `results/current_best.json` | 从兼容正式 Run 重建；不是 Accepted Solution，也不是跨设备全局最佳 |
| 机制解释与适用边界 | `docs/04_调优证据/Insight_Cards.md` | 只引用 Candidate、Run 和 Profile；不复制正式指标真值 |
| 发布证据 | `results/final_evidence/<release_id>/` | README、Report、Demo、Devpost 和 Replay 绑定同一 Release，不扫描“最新目录”猜版本 |
| Agent 控制状态 | `agent_state/` | 只保存恢复和审阅所需状态；不复制正式结果，不成为性能数据库 |
| 对外交付形态 | `submission/` | 从冻结源码和发布证据派生；不直接维护实现与指标 |
| 开发设计 | `docs/` | 描述稳定意图和边界；文件存在性、Run 与 Release 表达项目状态 |

## 步骤文档维护规则

1. 所有开发步骤使用 1–6 的数字编号，子步骤使用普通数字列表。
2. 本总览维护步骤关系、跨步骤边界、信息所有权和唯一完整目标树。各步骤文档维护本步骤的开发内容、涉及路径、开发判断和验证关注点。
3. 各步骤文档引用 `[开发步骤总览：完整目标文件树](./00_开发步骤总览.md#完整目标文件树)`，只列自身涉及路径，不复制完整树。
4. 赛题规则或官方 Benchmark 变化时，规则文档保存来源与事实；受影响步骤更新接口、Workload、测量或提交设计。历史经验只用于提出待验证方向。
5. 新路径只有在职责无法落入现有权威位置且存在真实消费者时加入目标树。临时分析、审计记录、状态周报、重复结果表和空模板不转化为长期工程结构。
6. 文档只维护稳定设计，不维护进度百分比、完成清单、任务队列或最近一次运行数字。仓库文件、测试、Run、Release、Commit 和外部提交链接直接表达这些事实。

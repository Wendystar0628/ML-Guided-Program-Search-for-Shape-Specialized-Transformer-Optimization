# 3. 全量验证与优化收敛

本步骤把代表性 Workload 上形成的候选证据扩展到完整官方 Workload，统一处理正式回归、有限参数 Search、跨 Workload 路由、失败隔离、资源记录和候选取舍。输出是可重建的 Measured Best、全量回归证据与候选采用建议；正式 `solution/` 的受控物化、干净环境重放和证据封存由发布步骤处理。

完整项目结构只在[开发步骤总览：完整目标文件树](./00_开发步骤总览.md#完整目标文件树)维护。赛题数学与接口边界见[赛题中文翻译](../../01_赛题规则/赛题中文翻译.md)和[允许与不允许的改造范围](../../01_赛题规则/允许与不允许的改造范围.md)。

## 1. 开发目标与边界

1. 把官方公布的全部 Shape、Dtype、Mask 和测量配置整理为单一机器可读 Workload Set，并由它派生人读矩阵。
2. 对候选执行全量正式回归，逐 Case 保存正确性、性能、执行路径、健康和失败事实。
3. 按 Variant Key 聚合同一配置的重复 Run，再在相同 Comparison Key 内重建 `current_best.json`，避免把局部最快、跨环境结果或 Search Screening 当作最佳实现。
4. 对少量、可解释、可预算的敏感参数使用有限 Search，并以完整正式 Run 复核 Finalist。
5. 根据跨 Workload 证据决定通用路径、最小 Dispatcher、等价 Fallback、继续优化或停止。
6. 形成候选采用建议、回退版本、资源摘要、失败边界和发布步骤可直接引用的 Run 清单。

这些工作可以按证据并行或回环推进。参数空间很小时可直接正式测量；某个 Case 暴露新缺陷时可回到候选修订；已有足够解释力的正式证据时不为形式重复 Profile。

## 4. 完整官方 Workload 矩阵

### 4.1 单一来源

完整 Set 沿用步骤 1 的 Schema，并绑定官方来源状态、引用、版本、有序 Case、Case 数量和 Set Hash。每个 Case 具有稳定 `case_id`，覆盖 Batch、Sequence、Hidden、Head、FFN、Layer、Dtype、Causal、Padding Ratio、Input Scale 以及官方新增的执行相关字段。

默认 Benchmark Shape 和预备语义组合只用于开发验证。官方清单信息不完整时可以使用明确标记为 provisional 的 Set；`official-all` 一类名称留给已经绑定完整官方来源的 Set。

人读 Workload Matrix、覆盖进度和结果表从机器可读 Set 派生，不手工维护第二份 Shape 清单。Set Hash 同时绑定来源和有序 Case，便于检查遗漏、重复、错序和混用版本。

### 4.2 每个 Case 的证据

全量矩阵的每一行至少能回链：

- Workload Set ID/Hash、Case ID 与完整 Signature；
- Candidate、Benchmark、Runner、环境、测量协议和执行配置身份；
- Correctness 总结果与正式 Run ID；
- 参考实现与候选 Median、Speedup、原始样本和重复聚合摘要；
- 请求路径、实际 `path_id`、是否使用声明式 Fallback；
- Run Health、评测墙钟、构建墙钟、失败类型和必要 Artifact；
- 该 Case 属于改善、噪声内无差异、明显回退、不支持或失败。

覆盖检查使用同一 Set Hash 核对 Case 数量、重复项和预期正式证据数。官方没有公布聚合或排名公式时保持逐 Case 展示，不自行制造“官方总分”；内部选择策略若使用权重或优先级，应明确标为内部决策且保留原始逐 Case 事实。

官方规则、Benchmark 或 Workload 清单变化会产生新的身份和 Set Hash。旧矩阵保留为 reference-only，不与新矩阵直接拼接。

## 5. 全量回归与 Measured Best

候选在全部官方 Case 上调用步骤 1 的正式 Runner 生命周期。每条 Benchmark/Regression 自带完整 Correctness、两侧原始样本、正式 Median、Speedup、实际路径和健康资格；历史 PASS、Profile、Microbenchmark 或 Shell 计时不替代本次正式事实。

重复 Run 数量、同实现噪声范围、健康拒绝规则和 Variant 聚合方式在候选取舍前确定。Variant 分数使用既定数量健康 Run 的 `median(run_speedup)` 并保留范围或 Spread；不挑最快一次，也不跨 Run 重拼原始样本。

| 名称 | 含义 | 改变方式 |
|---|---|---|
| Search Incumbent | 一个有限 Search 内的暂时领先配置或 Candidate | Search Driver 可更新 |
| Measured Best | 同一 Comparison Key 下，由 Eligible 正式 Run 推导出的最佳 Variant | 确定性 Query 重建 |
| Accepted Solution | `solution/` 指向的正式性能实现 | 发布选择受控物化 |

`current_best.json` 只是 Measured Best 的派生视图。它按 Variant Key 聚合同一实现与执行配置，再在相同 Comparison Key 内比较 Variant；损坏或删除后可从已提交 Run 重建。

Search、Screening、Profile、Diagnostic、Partial、Baseline 单侧测量、同实现对照、Correctness 失败后的诊断计时和比较键不同的历史 Run 均不进入该视图。Measured Best 不跨 GPU、Driver、框架、Benchmark、Runner、Workload 或协议形成全局最佳，也不自动成为 Accepted Solution。

## 6. 有限 Search 的新增工作

[步骤 2 的有限 Search](./02_性能分析与候选优化.md#7-按需使用有限参数搜索)服务代表性 Workload 上的候选生成和参数敏感性判断。本步骤只增加跨完整官方矩阵的参数收敛、Finalist 复核和路由选择。

### 6.1 适用信号与 SearchSpec

有限 Search 适合参数敏感性已有证据、参数类型与约束清楚、有效组合和预计 GPU 墙钟可预算、配置变化保持官方语义的路线。缺少这些信号时可缩小范围、改用直接候选或停止，不扩展为无约束 Grid、Bayesian Optimization、AutoML 平台或由模型逐配置拼接 Benchmark 命令的流程。

一次 Search 绑定一个 Environment、Workload、Base Candidate 和 SearchSpec。SearchSpec 记录参数 Schema、范围、条件约束、有效组合数、去重规则、Seed、确定性顺序、Cache/进程策略、单项与总预算、Screen/Formal 协议、Finalist 数量、Near-tie 规则和停止原因。

官方 Workload、Comparator 阈值、Accuracy Trial、正式 Repeat/Round，以及仅为候选放宽的输出 Dtype、TF32 或参考实现策略不作为调优参数。Candidate 自有 Compile、Backend、Graph/Runtime、Kernel 和注册参数可以形成 Variant，其解析结果进入 Execution-config Hash。

### 6.2 筛选与复核

固定 Driver 在一个 GPU 上串行执行配置，完成约束校验、去重、确定性排序、Correctness-first 筛选和紧凑写盘。Quick Screen 使用同一固定输入和 Timer，以两侧按块交替减少顺序偏差；它可以缩短 Warm-up/Repeat，但结果只称 Screening，不称正式 Speedup，也不做伪配对统计。

一次 Search 使用一个轻量 Run 保存共享 SearchSpec、Base Candidate、环境、Workload、预算、协议和停止原因。普通 Trial 只保存解析参数、顺序、状态、Correctness 摘要、Screening 摘要、墙钟和失败；不拆出完整 Raw Samples、独立日志或 Candidate 目录。

会生成不同 Python、Triton、CUDA 源码或任意脚本的配置形成独立 Draft 与冻结 Candidate，不藏在 Trial 行中绕过 Candidate 身份。长 Search 可以原子更新 Partial 文件，Query 与 Current Best 忽略未提交 Partial。

排名前若干项与噪声范围内的 Near-tie 固定为 Finalist，在清洁子进程中执行完整 Correctness 和正式双侧 Benchmark。只有 Finalist 正式 Run 能更新 Measured Best 与采用建议。配置极少且完整协议成本可接受时，可跳过 Quick Screen 直接正式测量。

## 7. 跨 Workload 取舍

### 7.1 结果分类

1. 广泛加速：大多数或全部官方 Case 稳定改善，资源与依赖成本可接受。
2. 局部加速：明确 Shape、Dtype、Mask 或 Backend 范围内改善，其他范围维持等价路径。
3. 噪声内无改善：重复 Run 不能支持稳定收益。
4. 明显回退：部分 Case 的下降超过噪声边界，需要修订、Fallback 或放弃候选。
5. 不支持或失败：构建、Correctness、OOM、Timeout 或 Backend 能力缩小声明范围。

全量矩阵用于 Final-vs-Baseline 回归。机制归因通常选择一个最低成本、最有区分力的 Shape、Feature、Route Contrast 或单项 Ablation，不把每个官方 Case 扩展成全因子消融。

### 7.2 Dispatcher 与 Fallback

不同 Workload 的最佳路径稳定分化，且收益覆盖分派开销、维护成本和新增正确性面时，可以采用最小 Dispatcher。路由条件使用少量明确的 Shape、Dtype、Mask 或 Capability 字段，并为每条 Run 保存请求路径、实际 `path_id` 和 Fallback 标记。

证据不支持稳定分流时，通用路径通常比复杂 Dispatcher 更合适。统一候选在部分 Case 上出现明显回退时，可以缩小候选作用域、使用已验证的等价 Fallback，或保留原 Accepted Solution。

Fallback 在正式执行中解析为声明式路径。优化路径发生 Build、OOM 或 Runtime Failure 时，不在同一 Run 中静默改跑 Baseline；验证 Fallback 使用新的干净子进程和独立 Run。Fallback 也保留相同数学语义，并在对应 Case 上形成自己的 Correctness 与正式计时证据。

参考实现自身无法执行的官方 Case 不能包装成“已覆盖”。Screening 排名、单次最小延迟、未复核 Profile 或意外回退也不决定 Dispatcher 路由。

### 7.3 缺陷回归

全量 Run 发现真实缺陷时保留最小复现条件、失败 Trial、Candidate 和代码路径。缺陷具有复发价值时在 `tests/test_regressions.py` 增加聚焦测试；一次性环境故障、普通无收益 Trial 和重复官方 Case 不转化为长期测试。

修复影响范围清楚时可以聚焦回归，影响范围不清楚或候选准备采用时使用完整官方矩阵。测试随真实缺陷增长，不预建第二套 Runner 或大型矩阵。

## 8. 失败隔离

失败 Outcome、Stage、Type、退出状态和 JSON 字段复用[步骤 1 的结构化 Run 契约](./01_测量基础与实现接口.md#8-结构化-run)。本步骤关注批量回归和 Search 中的污染隔离：

- 每个正式 Benchmark、Regression 和高成本 Build 使用新的受监督子进程与有限超时；
- OOM、Timeout、Runtime Error 或无法确认终止的进程不把 CUDA Context、编译状态或后台工作带入下一条正式 Run；
- 进程树终止状态不明确时暂停新的 GPU 正式任务并报告实际占用；
- Correctness 失败后的显式诊断计时保持 `eligible_for_comparison=false`；
- Search 中的 Unsupported、Compile Error、OOM 和 Timeout 作为普通结构化 Trial Outcome，不中断其余合法配置；
- 普通成功 Run 不复制完整 stdout/stderr，只有 Profile、构建或失败诊断确有价值时旁挂 Artifact；
- 临时文件、Partial 和中断样本不参与 Query、Measured Best 或采用建议；已提交 Run 不覆盖，重跑生成新 ID。

Search 取消或失败时保存已确认 Trial、停止原因和下一个安全位置；已消耗的 GPU/正式 Run 预算保持真实，不因恢复而重置。

## 9. 资源记录

环境身份与瞬时健康的分界沿用[步骤 1：环境身份与比较身份](./01_测量基础与实现接口.md#4-环境身份与比较身份)。本步骤面向完整矩阵增加紧凑汇总：

| 资源事实 | 汇总方式 |
|---|---|
| Forward Performance | 各 Case 的两侧 Raw Samples、Median、Speedup 和 tokens/s |
| Evaluation Cost | `evaluation_wall_time_s`、`compile_or_prepare_wall_time_s`、超时与完整矩阵总墙钟 |
| Execution Route | 各 Case 的 Direct/Fallback 路径与支持边界 |
| Failure Budget | OOM、Timeout、Build、Correctness 和 Unsupported 分布 |
| Build Capability | 实际使用的 Compiler/Triton/CUDA Extension 版本、依赖锁、配置、Cache 身份和冷构建墙钟 |
| Memory | 官方存在显存限制、真实 OOM、候选显存敏感或准备提出显存 Claim 时记录峰值和测量方法 |

CPU、RAM 和项目盘信息由单条 Environment Probe 或发布 rehearsal 引用，不在每条 Run 中复制。`forward_latency_ms` 进入官方 Speedup；完整评测与构建墙钟用于 Search 规模、等待时间和可行性判断，两种成本口径不混用。

未使用的 Backend、Profiler 或编译能力不构成资源要求。官方没有给出资源阈值时只报告实测事实，不自造“合格线”。

## 10. 优化收敛信号

| 决策 | 信号 | 建议动作 |
|---|---|---|
| 继续当前路线 | 正式收益稳定超过噪声；热点仍集中；参数空间和复核成本可预算 | 做一个更小的候选变化或有限 Search |
| 改变方向 | Profile 与假设冲突；候选只移动瓶颈；参数敏感性弱；相邻 Case 不泛化 | 更新机制判断并选择另一类成熟路径 |
| 引入最小 Dispatcher | 不同 Case 的最佳路径稳定分化，收益显著高于分派与维护成本 | 固定少量路由条件并全量回归 |
| 使用等价 Fallback | 优化路径在清楚范围外无收益或不支持，Fallback 已有正式证据 | 显式记录 Route、作用域和回退版本 |
| 保留原 Solution | 候选收益位于噪声内、资源成本过高、跨 Workload 回退或正确性风险不划算 | 输出否定证据和停止理由 |
| 结束优化 | 连续候选无收益、成熟路线 Plateau、预算或截止缓冲不足、环境不可比，或继续路线需要改变官方语义 | 选择最低风险、可重放的正确实现进入发布选择 |

停止是正常工程结论。未找到可信加速时可以标记 `no_verified_speedup`，保留 Correctness、失败边界和可复现证据；不把无收益包装成创新，也不声称跨设备、跨协议或跨 Benchmark 的全局最优。

官方规则、Benchmark 或 Workload 身份变化时，旧结论降级为带 Scope 的 reference-only。历史 Insight Card 可以启发路线，当前 Comparison Key 下具有正式资格的 Variant Run 决定取舍。

## 11. 候选采用建议与步骤交付

候选采用建议包含：

- Candidate ID、父 Source-tree Hash、Candidate Source-tree Hash 和 Execution-config Hash；
- 全官方 Workload 的正式 Run、Comparison Key 和 Workload Set Hash；
- 各 Case 的 Correctness、Median、Speedup、Spread、实际路径和分类；
- 已知失败、Unsupported、Fallback、上一 Accepted Solution 和回退办法；
- 构建、评测墙钟、依赖、显存与其他实际资源影响；
- 机制证据、反例、适用 Scope 和可选 Insight Card 引用；
- 建议采用候选、保留原 Solution、使用最小 Dispatcher、继续局部验证或停止的理由。

本步骤交付一个完整官方 Workload Set、全量正式回归矩阵、可重建 `current_best.json`、按需产生的有限 Search/Finalist 证据、资源与失败摘要，以及显式候选选择建议。没有使用 Search、Profiler、Dispatcher 或 Insight Card 时不制造空产物。

本步骤质量主要看三点：官方 Case 没有遗漏或重复；进入取舍的 Run 共享 Comparison Key、具有清楚的 Variant Key 和正式资格；失败、Fallback、资源成本与停止理由都能从仓库事实重建。

发布步骤根据明确选择受控物化唯一 Accepted Solution 和 Execution Manifest；Clean Replay、Official Replay 与证据封存均绑定物化后的 Solution 身份。本步骤不从 `current_best.json` 自动采用实现，也不扫描目录猜测“最新 Candidate”。

# 4. 发布证据与提交材料

> **文档定位**：把用户选定的实现物化为 Accepted Solution，形成可重放的发布证据，并从同一发布锚点派生公开仓库、README、Technical Report、Demo、Devpost 与 Submission。本文描述开发内容，不记录实现进度。
> **调度方式**：数字表示工作节点，不是执行顺序锁。Agent 可以合并、重排或迭代不改变数学语义、发布身份和证据含义的工作。
> **完整文件树**：[开发步骤总览：完整目标文件树](./00_开发步骤总览.md#完整目标文件树)。本文只列本步骤的主要文件落点。

公共契约直接复用：

- [步骤 1：测量基础与实现接口](./01_测量基础与实现接口.md)：Official Snapshot、Solution/Candidate 装载、Assembly、Correctness、Run Schema 与原子写入；
- [步骤 3：全量验证与优化收敛](./03_全量验证与优化收敛.md)：正式 Workload、比较键、证据资格、噪声规则、Fallback、资源记录、Measured Best 与候选采用建议；
- [赛题中文翻译](../../01_赛题规则/赛题中文翻译.md)：官方交付物与评审要求；
- [允许与不允许的改造范围](../../01_赛题规则/允许与不允许的改造范围.md)：数学功能与改造边界。

## 1. 本步骤形成的交付

1. 唯一 Accepted Solution 及与其匹配的 Execution Manifest；
2. 在干净环境产生的正式验证与 Official Replay；
3. 一个由显式证据封存的 `release_id` 和只读 Final Evidence；
4. 从发布锚点确定性派生的 Submission；
5. 引用同一事实的 README、Technical Report、Demo 和 Devpost；
6. 从实际 Public Repository URL 完成的公开复演记录。

主要文件落点如下：

| 落点 | 职责 |
|---|---|
| `solution/` | 唯一 Accepted Solution 源码与 Execution Manifest |
| `requirements.txt`、`requirements-lock.txt` | 最小直接运行依赖与精确运行锁 |
| `results/runs/`、`results/artifacts/` | 干净验证、官方重放和公开复演产生的事实 |
| `results/final_evidence/<release_id>/` | 一次发布的只读证据锚点 |
| `docs/04_调优证据/Insight_Cards.md` | 少量机制主张及其正式引用 |
| `README.md` | 评委和复现者的第一入口 |
| `submission/` | 按适用规则从发布锚点派生的提交产物 |

本步骤不重建 Solution Contract、Run 字段、Correctness 规则或 Measured Best 逻辑，也不新增发布数据库、第二套 Benchmark、第二份最终源码或 Dashboard。

---

## 2. 发布选择与 Accepted Solution 物化

步骤 3 给出候选采用建议和证据引用，采用本身始终是用户决策。用户可以随时选择采用 Candidate、保留既有 Solution 或回到其他实现；文档不把采用权绑定到固定阶段出口。

当用户选择 Candidate 时，受控 Acceptance 完成以下工作：

1. 核对选定 Candidate、父版本、源码闭包和执行配置身份；
2. 把选定源码闭包物化为唯一 `solution/`；
3. 更新 Manifest 中的入口、Source-tree Hash、依赖锁、声明执行范围和 Route/Fallback；
4. 保留原 Candidate、Run 和采用依据的不可变引用；
5. 清理重复的“最终实现”、失效入口和隐式本机路径。

保留既有 Solution 时，只核对其源码闭包、Manifest 和依赖身份，不制造一次无意义的源码复制。

采用决策与发布声明分开：用户可以采用证据覆盖仍有限的实现；该覆盖范围只决定 README、Report、Demo 和 Devpost 能声明哪些 Workload、环境、性能与可行性结论。源码或 Manifest 变化产生新的发布身份，与旧身份不匹配的 Run 保留为历史参考，不自动支撑新 Release。

适用规则作为发布输入处理，包括评测 GPU、Workload、误差阈值、运行时限、显存、依赖安装、编译缓存、报告格式、视频时长和提交形态。不同官方来源的评分公式保留来源与适用范围，不混算为自制总分。

## 3. Clean Replay

Clean Replay 在新的绝对路径、空虚拟环境、空普通 Run 目录和空构建 Cache 中执行，不继承开发期 `.venv/`、环境变量、隐式 `PYTHONPATH`、Agent Session、历史 Final Evidence 或未选 Artifact。

冻结快照与公开仓库复演覆盖不同故障面：

| 范围 | 关注点 | 输出 |
|---|---|---|
| 冻结快照 | 依赖、构建、正式 Workload、执行路由与官方装配 | 可供 Seal 选择的 clean Formal Run 和 Official Replay Run |
| 实际公开仓库 | Commit/Tag、README、下载权限、链接、Release Replay 与 Submission | 新的 Replay Run 和公开验收记录，不覆盖原 Claim |

Clean Replay 的开发内容包括：

1. 使用声明的 Python、最小直接依赖和精确运行锁建立环境，并检查依赖一致性；
2. 生成紧凑 Environment Probe，记录实际 GPU、OS、Driver、CUDA、Python、框架和 Backend；
3. 对计划声明的 Workload 执行 Solution 正式验证；
4. 在空 Staging 中装配 Accepted Solution 与只读 Official Snapshot，并从官方入口执行 Official Replay；
5. 对真实使用的编译 Backend 验证空 Cache 冷构建；未使用 Backend 不成为安装要求；
6. 记录验证墙钟、构建事实、OOM/Timeout 和确有声明价值的显存信息；
7. 演练 README 与 Demo 使用的入口、预期输出和证据路径。

依赖获取可以使用规则允许的固定来源；Solution、Runner、Official Replay 和 Demo 的运行边界不包含在线模型、Agent State 或网络请求。

失败生成新的诊断 Run，保留失败阶段、类型、短摘要和必要日志。源码、依赖、协议或 Assembly 的修订产生新的身份；Clean Replay 不改写既有 Final Evidence。

## 4. Final Evidence

Seal 从显式列出的支持 Run、Official Replay Run 与可选 Insight Card 引用构建 Final Evidence，不扫描“最新目录”，也不自动挑选最快结果。

一次发布保留的内容控制在以下范围：

| 内容 | 最小保留 |
|---|---|
| `release.json` | Release ID、Solution/Manifest、Source-tree Hash、依赖、环境、Workload、协议、支持范围与证据选择 |
| `runs/` | 支撑最终声明的正式 Run 自包含副本，包括重算结果所需的原始样本 |
| `artifacts/` | `release.json` 明确引用的 Official Replay、机制或失败解释产物 |
| Insight 引用 | 实际进入 Report 或 Demo 的零到少量 Card ID、文件 Hash 与正式证据引用 |
| `checksums.sha256` | 除自身外所有封存文件的完整校验和 |

Final Evidence 通过 Manifest 和 Source-tree Hash 绑定唯一 Solution，不复制第二份可修改源码。`release_id` 与公开 Commit/Tag 的映射由 README、Devpost 或 GitHub Release 页面记录，并在公开复演时核对该 Commit 中的源码身份；Commit/Tag 不写回参与自身 Seal Hash 的文件。普通 Shell 输出、开发期 Trace、Search 全量中间点、Agent Transcript、未选历史结果和完整成功日志不进入证据包。

Seal 重算输入身份、证据引用、Case 覆盖和 Checksum，并使用临时目录原子提交。失败不留下可冒充正式发布的完整目录；形成的发布目录按只读证据使用，新发布获得新的 `release_id`。

证据覆盖决定声明范围：覆盖全部适用官方 Case 的 Release 可以支持全量结论；局部覆盖可以形成明确标注 Scope 的实验性或局部发布。官方提交本身要求的覆盖仍按适用规则表达，不以文档自造门槛。

README、Report、Demo 和 Devpost 的数字表从 `release.json` 与封存 Run 派生，派生材料不反向修改正式事实。

## 5. Submission 装配

`submission/` 从明确的 Release、公开 Commit/Tag 和适用提交格式派生，不作为源码或指标真值源。

装配逻辑使用 Allowlist 选择 Accepted Solution 源码闭包、Manifest、必要依赖声明、官方要求文件和提交材料。官方要求单文件时，从同一 Solution 确定性生成；官方要求仓库时，保留清晰项目结构。装配产物复用步骤 1 的 Assembly 契约完成官方入口重放，并记录 Assembled Output Hash。

装配排除 `.venv/`、Cache、`__pycache__/`、开发期普通 Run、未选 Artifact、Agent State、Secret、机器绝对路径和本地凭据。密码保护或第三方材料只在许可允许时再分发；其余内容保留合法链接、来源说明或项目自写摘要。

发布检查同时覆盖 Git 历史和生成文件中的 Token、用户名、私有下载地址、无许可资产及第三方商标。Submission 形态变化时重新装配，不维护一份平行演进的提交专用实现。

## 6. README

README 面向评委与第一次复现项目的人，首屏优先提供：

1. 一句话问题定义与解决方案；
2. Release ID、Commit/Tag 与 Accepted Solution 入口；
3. 代表性正确性和性能结论，以及 Final Evidence 链接；
4. 已验证环境、最小安装、Smoke、正式 Verify 和 Release Replay 入口；
5. 预期输出、预计墙钟、结果位置、运行时网络边界、Fallback 和局限。

其余内容说明项目导航、执行路径、Workload 覆盖、证据校验、常见失败、报告和视频链接、更多时间下的改进及团队贡献。完整树只引用 00，不在 README 和本文维护竞争版本。

README 中的数字、单位、舍入、Workload 名称和支持范围从同一 Release 派生。Smoke 明确标为快速检查，不冒充正式性能结果；示例输出和截图标注对应的 Release ID。

## 7. Technical Report

Technical Report 按问题—机制—证据—边界组织，覆盖：

1. 赛题目标、数学边界、目标硬件与 Workload；
2. CPU、RAM、磁盘、GPU、Driver、CUDA、Python、框架和实际 Backend；
3. Baseline 观察、瓶颈机制、Accepted Solution、Dispatcher/Fallback 与复杂度取舍；
4. Correctness 结论和正式 Workload 结果表；
5. 代表性机制对照、Scope、反例和回退；
6. Clean Replay、依赖、构建、验证墙钟、显存及 OOM/Timeout；
7. AI Skills、模型、工具、API、Library、Framework、数据和其他资源；
8. 潜在受益者或使用场景，以及延迟、吞吐、资源或开发效率收益如何形成实际价值和可迁移范围；
9. 局限、未验证范围、更多时间下的改进与团队贡献。

AI 与 Agent 说明记录实际输入、动作、输出和人工验证。进入报告的 Agent 闭环回链真实 Session、Skill、Candidate、Formal Run 与后续决策；拒绝 Candidate 或按预算停止也按真实结论表达。隐藏推理、聊天长度、Agent 数量和工具数量不作为工程证据。

Innovation & Problem Insight 使用一条轻量链路：问题、Observation、Hardware Mechanism、可证伪 Prediction、最小 Candidate 变化、正式 Contrast、Conclusion、Scope 与 Fallback。每项主要机制保留一个最有区分力的对照即可。成熟 SDPA、编译器、Triton、CUDA、Autotune 或 Agent 的采用写成工程选择，除非证据能支持更具体的原创机制或硬件适配。

## 8. Demo

Demo 复用同一冻结快照、Release ID 和证据表，以可读终端和必要的静态图表完成叙事：

1. 问题、目标与数学边界；
2. Accepted Solution、Runner、Final Evidence 与 Submission 的关系；
3. 快速验证及其与正式结果的区别；
4. Correctness、正式 Benchmark、实际 Path/Fallback 与证据入口；
5. 一个代表性机制对照及其 Scope；
6. 全量或明确范围内的结果、支持环境、资源事实和局限；
7. 公开仓库、Technical Report 和证据链接。

Agent 只在真实冻结闭环具有展示价值时出现，画面展示 CLI、Candidate、Runner 反馈和后续决策，不演示未实现能力。最终视频按适用规则控制时长，上传 YouTube 并设为 Public；退出账号或无痕状态检查播放、清晰度、字幕和说明栏链接。无许可商标、音乐、视频、图片或代码不进入视频。

---

## 9. Devpost

Devpost 按问题、洞察、方案、技术执行、结果、影响、可行性、局限与链接组织，并说明潜在受益者或使用场景、工程收益如何转化为实际价值及赛题外可迁移范围；同时列出实际使用的开发工具、API、Library、Framework、数据集和其他资源，未使用的类别明确为无或不适用。

页面链接公开仓库、固定 Commit/Tag、Release ID、Technical Report 和 Public YouTube。结果摘要从 Final Evidence 派生，与 README、Report 和视频保持同一单位、舍入、Workload 名称和 Scope。成果列表只纳入冻结证据能够支持的 Backend、优化、Agent、兼容范围和资源事实。

提交字段和限制取自适用官方页面或组织方说明。不同来源存在差异时保留来源与适用范围，不自行平均权重或补造排名公式。

## 10. 评审表达

| 评审关注点 | 表达主线 | 直接证据 |
|---|---|---|
| Technical Execution | 唯一源码、清晰职责、可执行契约、干净重放、可解释 Fallback | Manifest、Formal Run、Raw Samples、Official Replay、Checksum |
| Innovation & Problem Insight | 从真实瓶颈到硬件机制、最小改动、可证伪对照和边界 | Observation/Profile、Insight Card、正式 Contrast、反例 |
| Impact & Relevance | 在官方 Workload 上给出可重复收益、覆盖范围、潜在受益者、实际价值和赛题外可迁移边界 | 各 Case 延迟、Speedup、Path、资源、覆盖表和局限 |
| Feasibility & Practicality | 在声明环境中可安装、构建、运行、失败退出或回退并公开重放 | Clean Replay、依赖锁、环境、墙钟、Build、OOM/Timeout |
| Presentation & Communication（仅适用 Final Event） | 问题、机制、结果、限制和价值形成同一可追踪叙事 | 同一 Release 的 README、Report、Demo 与 Devpost |

Technical Execution 不用组件数量、Agent 数量或临时终端数字证明。Feasibility 聚焦声明范围内的最小依赖、Clean Replay、资源成本、Fallback 和 Unsupported 边界，不为评分扩展到题目范围外的服务化、数据库、集群或生产部署。

Agent 的可恢复执行、Candidate 生命周期和结果回链可以支持 Technical Execution；本机证据实际改变路由、Candidate、拒绝或停止决策并形成正式对照时，才支持 Problem Insight。其他 Agent 使用保持为开发工具说明。

## 11. 公开仓库复演与完成定义

公开仓库包含所有对外声明依赖的 Solution、Runner、Assembly、测试及可选 Agent 源码，并使用适量英文注释解释非显然的工程与硬件决策；生成状态、Secret、缓存和本机路径仍排除。公开复演从实际 Public Repository URL 获取固定 Commit 或 Tag，在新的绝对路径和空环境中检查：

1. 匿名访问仓库、Release、Final Evidence、报告、视频和许可证；
2. 按 README 安装最小依赖并完成 Smoke；
3. 使用显式 `release_id` 执行 Release Replay，生成新的 Replay Run；
4. 从空 Staging 装配 Submission 并完成 Official Replay；
5. 核对 Solution、Manifest、Commit/Tag、Release 和 Assembled Output 身份；
6. 检查仓库内链接、图片、报告、视频、Devpost 和证据入口；
7. 检查 Secret、绝对路径、缓存、Agent State、版权、商标与再分发许可；
8. 对照适用官方表单检查字段、文件、格式、大小、视频时长和链接。

公开复演产生的新 Run 证明仓库可复现，并与封存参考摘要比较；它不覆盖 Final Evidence 中支撑原 Claim 的 Run。GPU 延迟按步骤 3 的健康与噪声规则比较，不要求逐位相等。

本步骤的完成定义是：公开 Commit/Tag 映射到唯一 Accepted Solution 和 Final Evidence；声明范围能从封存 Run 重建；Clean Replay 与公开仓库复演可执行；Submission 能从发布锚点重新装配；README、Technical Report、Demo 和 Devpost 引用同一事实；未验证能力、过期数字、Secret、开发机路径和无许可材料不进入对外成果。

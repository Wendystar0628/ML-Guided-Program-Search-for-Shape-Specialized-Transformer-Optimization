# 开发步骤 1：测量基础与实现接口

> 本文定义官方 Benchmark 快照、Workload、环境身份、Runner、结构化 Run、Solution/Candidate 装载与 Correctness 契约，不记录实现进度。项目完整且唯一的文件树见 [开发步骤总览：完整目标文件树](./00_开发步骤总览.md#完整目标文件树)；本文只列本步骤涉及的主要路径。

## 1. 目标与边界

本步骤把“实现是否正确”和“性能数字是否可信”收敛为一套确定性公共接口，供后续性能分析、候选优化、全量验证、发布和 Hardware-aware Agent 复用：

1. 保存字节不变、来源可追溯的官方 PyTorch Benchmark；
2. 用唯一机器可读 Workload Set 表达 Case、顺序和来源；
3. 分离环境、裁判、源码、Workload、测量协议与瞬时健康身份；
4. 由 Runner 直接产生结构化事实，不解析终端文本获取正式数字；
5. 用结构一致性、官方原样重放和同实现双侧控制验证测量系统；
6. 以显式契约装载 Solution 和冻结 Candidate；
7. 复现官方 Correctness、Warm-up、计时、Median 与 Speedup 语义；
8. 每项托管测试原子写入一条可重算的 Run JSON。

本步骤不选择优化机制，不展开全量回归、发布封存或提交材料，也不建设实验数据库、Dashboard 和第二套 Benchmark。Profiler、Search 与 Agent 只复用这里的身份和结果契约。

## 2. 事实来源与官方语义

| 顺序 | 来源 | 用法 |
|---:|---|---|
| 1 | 本届最新官方规则、问答、Workload 与评测说明 | 决定最终约束 |
| 2 | 官方 Benchmark 的可执行行为 | 决定当前接口、Correctness 与计时语义 |
| 3 | 项目 Runner、身份、持久化和噪声设计 | 保证可解释、可比较与可重放 |
| 4 | 历史经验、Profiler 观察与跨设备结果 | 只提出待验证假设 |

规则阈值与脚本默认值分别保存。两者存在差异时不自行合并；Run 记录实际配置，官方更新通过新的 Benchmark、Workload 或协议身份体现。

本项目采用 PyTorch 路线，优化对象仍是同一个 Transformer Layer：

| 项目 | 稳定语义 |
|---|---|
| 入口 | UserOptimizedTransformer |
| 调用 | forward(x, valid_token_mask=None) |
| 输入输出 | 保持 [B, S, D]、设备与调用约定兼容 |
| 权重 | 默认严格复制；布局变化提供等价转换 |
| 数学结构 | 保留 Attention、Mask、Residual、LayerNorm、FFN、GELU 与最终归一化 |
| 性能指标 | 完整 Transformer Forward 的端到端 Median；Speedup 为 Baseline Median 除以被测实现 Median |
| Shape 特化 | 允许选择不同等价路径，实际路径和 Fallback 进入 Run |

算子融合、布局调整、Compiler/Runtime、成熟 Backend、低精度、Tensor Core、Triton、CUDA Kernel 和有限 Dispatcher 都可由 Correctness 与正式测量裁决。替换注意力类型、引入新稀疏模式、改变 Head/Hidden/FFN/Layer 数量、替换 GELU、删除或改写 Residual/LayerNorm，以及用剪枝、低秩近似或 Token Dropping 换取速度，属于改变模型定义。

## 3. 官方快照与 Workload

### 3.1 官方快照

official/ 保存官方 Benchmark 的字节级快照。official/snapshot.json 记录来源或定位信息、获取时间、原文件名、字节数和 SHA-256。组织方没有提供独立校验值时，该 Hash 称为 Acquisition Checksum，不表述为组织方签名。

Runner 和测试只读 Snapshot；装载、结构化输出与装配逻辑位于 runner/。官方文件更新形成新的 benchmark_hash，旧的一致性结论和比较结果保留原身份作用域。

official_baseline_identity 由 benchmark_hash、Baseline 符号和 Baseline Loader Contract 版本规范化计算，并由 Run Schema 校验器重算，不另建 Registry。

### 3.2 Workload Set

runner/workloads/ 是 Workload Set 的唯一机器可读来源。README、报告和人读矩阵从 Set 派生，不维护第二份 Shape 清单。

| 字段 | 内容 |
|---|---|
| schema_version | Schema 版本 |
| workload_set_id | 不可变命名 ID |
| source | 来源状态、引用与版本 |
| ordered_cases | 稳定执行顺序中的 Case |
| case_count | Case 数量 |
| workload_set_hash | 对除自身外的规范化完整内容计算的 SHA-256 |

每个 Case 使用稳定 case_id，核心 Signature 为 B、S、D、H、F、L、dtype、causal、padding_ratio。input_scale、Seed、Accuracy Trial、Warm-up、Repeat 和 Round 作为输入生成或测量配置进入正式 Run。

官方清单未公布时，来源状态使用 provisional，语义覆盖无 Padding/非 Causal、Padding/非 Causal、无 Padding/Causal、Padding 与 Causal。正式名称只表达真实来源，不把脚本默认 Shape 或预备矩阵写成官方全量清单。

## 4. 环境身份与比较身份

| 分类 | 保存内容 | 作用 |
|---|---|---|
| environment_id | OS、Shell Backend、GPU Identity、Compute Capability、显存、Driver、CUDA Runtime、Python、PyTorch；实际使用时加入 Compiler、Triton 和相关依赖版本 | 稳定执行环境 |
| run_health_snapshot | 温度、利用率、空闲显存、外部 GPU 进程和瞬时负载 | 本次 Run 的健康与噪声资格 |
| 独立身份 | Benchmark、Runner、Solution/Candidate、Workload、Measurement Protocol | 组成比较键 |

CPU、RAM 和项目盘信息由单条 Environment Probe 保存，不在每个 Run 重复。静态 Probe 不初始化 GPU；CUDA 可用性、小 Tensor、扩展编译和 Profiler 自检属于 Active Probe，由类型化 Runner/Tool 在受监督进程中执行。CPU 运行只标记为接口 Smoke，不产生 GPU 性能 Claim。

Windows 与 WSL 形成不同环境身份。跨设备、跨环境或不同完整比较键的 Run 可启发假设，不直接进入当前设备的 Measured Best。

| 键 | 组成 |
|---|---|
| comparison_key | Environment、Benchmark、Runner、Official Baseline Identity、Workload、固定 Measurement Protocol |
| variant_key | comparison_key 加 Candidate Source-tree Hash 与 Execution Config Hash |

同一 Variant 的健康正式 Run 先聚合，再在相同 comparison_key 内比较实现。Candidate 身份不进入公共比较条件。

## 5. Runner 与测量语义

### 5.1 Runner 职责

Runner 是 Environment Probe、Correctness、Benchmark、Profile、Search、Replay、查询和结果写入的确定性入口。它直接调用官方低层能力并返回结构化结果；stdout/stderr 只用于展示或必要诊断。

| 环节 | 保持的语义 |
|---|---|
| 配置 | Seed、数值开关、Config 校验和实际命令 |
| 装载 | Baseline 与显式 Target 按冻结身份装载 |
| 初始化 | 模型构造、严格权重复制、Device 与 eval() |
| Correctness | 完整 Trial、官方 Comparator、失败策略和附加契约 |
| 性能输入 | 固定输入，与 Accuracy 输入分离，生成不计时 |
| Warm-up | Baseline 与被测实现分别执行 |
| 计时 | CUDA Current Stream Event，按 Round 交替两侧先后 |
| 聚合 | 汇总全部原始样本后求 Median，再计算 Speedup |
| 持久化 | 计时区间外校验并原子提交 Run |

正式 Benchmark 或 Regression 使用新的受监督子进程，从冻结身份完整执行。Build、OOM、Timeout 或取消形成独立终态；相应进程退出后不复用其 CUDA Context。Fallback 在 Correctness 与计时前解析并记录，运行中意外失败不在同一正式 Run 静默切换到 Baseline。

### 5.2 Runner parity

| 层次 | 方法 | 证明范围 |
|---|---|---|
| 结构一致性 | 固定 Fixture 与受控假 Timer | Seed、输入/Mask Digest、模型与权重、调用次数、Warm-up/计时边界、Round 顺序、样本数、全样本 Median、Speedup 公式与失败分类 |
| 官方原样重放 | 原始 Snapshot 或确定性装配产物，在新进程使用官方原有参数 | CLI 可见配置、退出码、Accuracy 摘要和聚合口径 |

结构 Fixture 同时覆盖已知正确实现与最小已知错误实现。官方 CLI 未输出的权重身份、Round 顺序和原始样本不从终端文本推断，由结构 Fixture 与 Runner 事实证明。

benchmark_hash 与 runner_protocol_hash 共同绑定一致性认证。身份变化使旧认证降级为历史参考。

同实现双侧控制让 Official Baseline 作为比较两侧运行，机器标识为 target=aa_control。重复次数、健康拒绝条件、噪声边界和 Variant 聚合方式在观察 Candidate 结果前冻结。Ratio 分布与 1.0 明显不相容时，该环境或协议不产生性能 Claim；排查外部负载、热状态、缓存、进程状态和测量顺序。

### 5.3 官方计时

| 项目 | 语义 |
|---|---|
| Accuracy 输入 | Trial 使用 seed + trial |
| 性能输入 | 使用 seed + 100000，生成不计时 |
| CUDA Timer | 调用者 Current Stream 上的 CUDA Event |
| Round 顺序 | 奇偶 Round 交替两侧先后 |
| 单次聚合 | 合并全部 repeats × rounds 样本后直接求 Median |
| Speedup | baseline_median_latency / optimized_median_latency |
| tokens/s | 使用 B × S，包括 Padding Token |

参考脚本默认使用 Accuracy Trial 5、Warm-up 20、Repeat 100、Round 3；一次双侧评测至少包含 650 次 Forward，另有构造、权重复制、编译、同步和进程开销。Run 因此分开保存 forward_latency_ms、evaluation_wall_time_s 与可选 compile_or_prepare_wall_time_s。

两侧的 Compile、Compile Mode、TF32、Dtype、Matmul Precision、Warm-up、Repeat 和 Round 进入协议或 Variant 身份。原始延迟数组保留在 Run 中。Profiler、Microbenchmark、Search Screening 和 Shell 临时计时只服务诊断或筛选，不替代完整 Transformer 正式计时。

## 6. Solution、Candidate 与 Assembly

### 6.1 装载契约

| 契约项 | 约定 |
|---|---|
| 正式源码根 | solution/ |
| 入口文件 | solution/transformer.py |
| 入口符号 | UserOptimizedTransformer |
| 构造 | 使用官方 Transformer Config |
| Forward | 接受 x 与可选 valid_token_mask，返回 [B, S, D] Tensor |
| 权重复制 | 默认严格复制；布局变化可提供等价转换钩子 |
| 源码身份 | 对完整可执行闭包的排序相对路径和原始字节计算 source_tree_hash |

模块导入不初始化 GPU、不联网、不安装依赖、不执行 Benchmark。Loader 使用显式路径，不依赖 cwd、父目录 PYTHONPATH 或同名模块偶然解析。

### 6.2 Solution 与 Candidate 身份

solution/manifest.json 描述入口、Source-tree Hash、来源 Candidate、依赖锁路径与 Hash、声明执行范围、path_id、Dispatch/Fallback 和上一 Accepted Source。Source-tree Hash 排除 Manifest、Cache 与生成物；Manifest 另有避免自引用的完整内容 Hash。

可变实验位于 candidates/_drafts/<draft_id>/solution/**。Freeze 将完整可执行闭包原子物化为 candidates/<candidate_id>/candidate.json + solution/**；冻结目录只读，源码变化产生新身份。

candidate.json 保存 candidate_id、parent_source_tree_hash、source_tree_hash、entry_file、created_at、created_by，实际需要时增加最小 Build 字段。正式 Candidate Target 只接受冻结 ID，不接受 Draft、任意路径或临时目录。candidate_execution_config_hash 绑定 Compile、Backend、Graph/Runtime、构建产物和已解析参数。

### 6.3 Assembly

runner/assembly.py 在空 Staging 中把冻结源码闭包绑定到官方允许修改的实现与权重复制区域，保持其他 Harness 行为一致，并在新进程使用官方原有参数运行。

装配过程核对：

1. Official Snapshot Hash；
2. Solution 或 Candidate Source-tree Hash；
3. Assembly Tool Hash；
4. Assembled Output Hash。

Assembly Tool Hash 覆盖 runner/assembly.py 及其声明的项目内可执行依赖。装配产物不依赖 Monkey Patch、开发机绝对路径、父目录 PYTHONPATH 或临时进程状态，也不成为第二份性能源码。

## 7. Correctness

官方脚本先检查输出 Shape，再将两侧输出转换为 FP32，检查有限值，并逐元素使用“绝对误差满足阈值，或相对误差满足阈值”的条件。

| 来源 | 相对误差 | 绝对误差 | 条件 |
|---|---:|---:|---|
| 官方赛题文字 | < 0.02 | < 0.002 | 未明确 AND/OR |
| 参考脚本默认 | <= 0.01 | <= 0.001 | OR |
| 最终评测 | 按最新脚本或参数 | 按最新脚本或参数 | Run 保存实际值 |

项目开发采用参考脚本默认值作为更严格的内部门槛，同时保留官方文字口径。Correctness 失败默认不进入正式性能计时；显式 benchmark_on_failure 只产生不可比较的 Diagnostic。

确定性契约测试覆盖：

1. mask=None、全 True Mask、混合有效/无效 Token、Causal 与 Padding；
2. 严格权重复制和等价权重转换；
3. 输出 Shape、Device、Dtype 与有限值；
4. 输入、Mask、Parameter 和 Buffer 不被意外原地修改；
5. 输入甲、输入乙、输入甲交替调用时无调用历史依赖；
6. 显式装载、完整本地依赖闭包和无导入副作用。

每个组合先使用官方 Comparator，再检查项目附加不变量。Dtype 差异按独立 Contract 字段保存，不伪装成官方 Comparator 失败。

Shape mismatch、Tolerance failure 与非有限输出记录为 Correctness 阶段的 invalid_output。严格 JSON 不保存 NaN 或 Infinity；诊断值非有限时写 null 并记录数量、类型和代表索引。非严格权重复制保存 Missing/Unexpected Key；等价映射缺少独立证据时，相应 Run 不进入可比较集合。

## 8. 结构化 Run

| 维度 | 值 | 含义 |
|---|---|---|
| preset | smoke、formal | 验证严谨度 |
| target | baseline、aa_control、solution、candidate | 被测对象 |
| run_kind | benchmark、regression、probe、profile、search、official_replay、replay、diagnostic | 记录类型 |

| 字段组 | 保存内容 |
|---|---|
| 身份 | Run、时间、Kind、Preset、Target、Outcome |
| 代码与裁判 | Benchmark、Runner、Official Baseline Identity；Solution/Candidate 再加对象 ID、Source-tree 与 Execution Config Hash |
| 环境与 Workload | environment_id、Health Snapshot、Set/Case ID 与 Hash、完整 Signature |
| 协议 | Seed、Tolerance、Trial、Timer、Warm-up、Repeat、Round、Timeout、Compile、Matmul Precision、TF32、权重复制 |
| Correctness | 总体结果、Trial、误差、失败元素、Warning 与失败定位 |
| Performance | 原始延迟、Median、Speedup、健康、噪声和比较资格 |
| Failure/Artifact | Stage、Type、短消息、退出状态与可选相对路径 |
| 可选来源 | 后续 Agent Run 可引用 Session、Action、Request、Attempt、由第 2 步定义的 `tuning_layer_id`、`tuning_layer_name` 与 Skill，不拆独立 Provenance |

| Target | Performance 内容 | 用途 |
|---|---|---|
| baseline | 单侧 Baseline 原始样本与 Median | 当前环境参考 |
| aa_control | 两臂 Baseline 样本、Median 与 Ratio | 测量偏差控制 |
| solution | Baseline/Solution 样本、Median 与 Speedup | 正式实现比较 |
| candidate | Baseline/Candidate 样本、Median 与 Speedup | 冻结候选比较 |

eligible_for_comparison 由 Runner 根据 Run 类型、Parity、Correctness、身份、样本、健康、噪声和 Diagnostic/Partial 状态推导，外部输入不能直接设为真。Correctness 失败、Unsupported、Build/Runtime/OOM/Timeout 和取消均形成明确失败 Run，不进入比较集合。

普通 Run 写入 results/runs/<run_id>.json：同目录临时文件通过 Schema 校验和 Flush 后原子替换；最终 JSON 存在表示提交完成，残留临时文件不参与查询，已提交 Run 不覆盖。原始样本直接保存在 Run JSON，只有失败、Profile 或 Replay 确有需要时旁挂 Artifact。

## 9. 开发安排

以下数字是建议顺序，不是运行时状态机。开发者或 Agent 可按仓库事实合并实现、调整局部顺序或提前验证高风险接口。

1. 定义官方快照、Acquisition Checksum、Benchmark Hash 与 Baseline Identity。
2. 定义 Workload Set、Case Signature、来源状态、顺序和 Hash。
3. 定义 Environment、Health、Comparison 与 Variant Identity。
4. 定义统一 Run Schema、失败分类、比较资格和原子提交。
5. 实现官方生命周期的结构化 Runner Adapter。
6. 建立正确/错误 Fixture、假 Timer 与结构一致性测试。
7. 建立官方原样重放和同实现双侧控制。
8. 建立 Solution/Candidate Loader、完整源码闭包和身份校验。
9. 建立确定性 Assembly 与四类 Hash 校验。
10. 扩展 Mask、Causal、Padding、权重、Dtype 和状态契约测试，并验证 Baseline、Solution 与冻结 Candidate 均生成可重算 Run。

## 11. 验收与工程约定

本步骤的证据应能说明：

1. Snapshot、Workload、环境、协议、源码与 Runner 身份可重算；
2. 正确 Fixture 通过，已知错误 Fixture 失败且不产生可比较数字；
3. 官方原样重放与结构一致性分别覆盖其可观察范围；
4. 同实现双侧控制不产生优化 Claim，异常偏差会阻止相应比较；
5. Solution 与冻结 Candidate 由显式路径装载，完整源码闭包可核对；
6. Mask、Causal、Padding、权重、Dtype、状态和交替输入契约可验证；
7. Run 保留原始样本、实际协议、Correctness、失败与身份，聚合值可重算；
8. 中断、OOM、Timeout、Unsupported 与写盘失败不会冒充成功结果；CPU Smoke、Profiler、Screening 与 Shell 临时计时不会进入 GPU Claim。

项目自有源码的标识符、Docstring、注释、CLI 帮助、错误和状态文本使用英文；中文文档解释设计和边界。注释聚焦非显然的 Fusion、Layout、精度、Stream、Dispatch、Fallback 与身份原因。

正式事实只由 Runner 写入，solution/ 是唯一正式性能源码根，派生视图可由 Run 重建。可选 Backend、Kernel、Profiler Artifact 与回归测试由真实实现或缺陷触发，不为展示架构预建空目录。文档不维护进度清单，真实状态由仓库和测试决定。

# 2. 性能分析与候选优化

> **本步骤目标**：把可信测量转化为一个有机制依据、可被否定、可独立重放的优化候选，并在代表性 Workload 上完成第一条正式端到端证据闭环。
>
> **执行方式**：下文数字表示建议推进顺序，不是固定状态机。Agent 可依据已有证据跳过重复 Profile、回到测量校准、切换优化层、并行准备少量互斥候选，或在收益与风险不匹配时结束分支。
>
> **目录口径**：完整目标文件树只维护在 [00_开发步骤总览](00_开发步骤总览.md)。本文只列本步骤涉及的文件落点，不维护另一棵完整树。

## 1. 开发结果与范围

本步骤交付的是“候选证据包”，不是自动更新后的正式 Solution。它回答五个问题：

1. 代表性 Workload 的主要 GPU 开销在哪里；
2. 哪个保持数学语义的改动最值得先验证；
3. 哪项观测支持该判断，什么结果会否定它；
4. 隔离候选在相同比较口径下是否正确、是否获得稳定端到端收益；
5. 后续全 Workload 验证应保留、修订、换层还是放弃哪条路线。

建议把范围控制在一个主假设、至多一个备选假设和少量候选。已有兼容证据足以作出选择时，可直接准备候选；环境漂移、同实现对测异常或比较身份不完整时，可先回到测量校准。Profile、搜索和候选数量都由信息增益与预算决定，不作为形式化任务清单。

本步骤不自动覆盖 `solution/`，不把局部最优写成正式采用版本，也不承担全部官方 Workload、最终 Fallback、发布封存或 Agent Runtime 建设。全量覆盖、跨 Workload 取舍与候选采用由后续开发步骤处理。

## 2. 证据资格与比较口径

优化空间遵循 [允许与不允许的改造范围](../../01_赛题规则/允许与不允许的改造范围.md)：可以改变执行方式、融合边界、Kernel、数据布局、精度路径和硬件参数；数学功能、公开接口、权重含义与 Transformer 结构保持一致。

| 证据项 | 本步骤采用的口径 | 不满足时的处理 |
|---|---|---|
| 数学与接口 | 输入输出、Mask、Causal、Residual、LayerNorm、Attention、前馈层和权重映射保持等价 | 候选归为越界或待修订，不形成性能结论 |
| Correctness | 使用冻结的 Comparator 配置和目标语义组合，保存紧凑 Trial 摘要 | 计时若仍被执行，只标为诊断；不进入候选比较或洞察结论 |
| 正式性能 | 完整 Transformer Forward 的双侧端到端测量，以两侧 Median 计算 Speedup | Kernel Microbenchmark、Profiler 时间和快速筛选结果只用于选路 |
| 可比身份 | 环境、官方 Benchmark、Runner、Baseline 身份、Workload 和固定测量协议一致 | 结果降级为参考证据，不与本轮候选直接排序 |
| 重复与噪声 | 使用候选出现前已经确定的重复数、健康规则和噪声边界；按健康正式 Run 的中位结果判断 | 不挑最快一次，不用偶然最小样本晋升候选 |
| 实际执行路径 | Run 记录请求路径、实际路径与 Fallback；意外构建、内存或运行失败显式落盘 | 不把静默退回 Baseline 的结果写成候选收益 |

正式比较继续保留两侧原始延迟样本、各自 Median、Speedup、运行健康与完整身份。Profile 和快速搜索可以改变下一步选择，但不能替代端到端裁决。

## 3. 建议开发顺序

### 1. 选择代表性 Workload 与比较身份

优先选择对最终结果有解释力的 Case：Baseline 端到端成本高、覆盖典型 Shape/Mask/Dtype、疑似热点集中，或能区分两条候选机制。官方 Workload 已明确时直接引用其稳定 Case；尚未明确时使用可替换的预备 Case，并标清来源范围。

为本轮候选批次固定以下比较信息：

- 环境与设备身份；
- 官方 Benchmark、Runner 与 Baseline 身份；
- Workload 与输入生成配置；
- Comparator、Seed、数值策略、Warm-up、Repeat、Round、Timer 与 Compile 策略；
- 同实现对测得到的噪声和健康判定规则；
- 可使用的 Backend、候选数、正式测量次数、GPU 时间和总墙钟预算。

同实现对测偏离噪声规则、GPU 健康异常或环境身份变化时，优先刷新测量事实。该选择是为了避免在不稳定比较面上优化，不要求每次实验重复建设测量系统。

### 2. 采集足以改变选择的 Profile

Profile 围绕一个决策问题采集，而不是为了留下完整 Trace。建议先用 PyTorch Profiler 或 Nsight Systems 判断时间花在 Attention、Projection、前馈层、归一化与残差、小算子 Launch、同步还是内存流量；确认单一热点后，再考虑用 Nsight Compute 深挖 Occupancy、吞吐、带宽或 Stall。

一条可复用 Profile Run 记录：

- Profiler 名称、版本与设置身份；
- Candidate 或 Solution 源码身份、环境和 Workload；
- Trace 或报告的 Artifact 路径；
- Top Operator/Kernel 的绝对时间和占比；
- 主要瓶颈类别；
- 与当前机制判断直接相关的少量指标；
- 采集失败、工具不可用或数据受干扰时的降级说明。

大型 Trace 放在对应 Run 的 Artifact 目录，Run JSON 只保留定位所需的摘要。已有同一比较范围的 Profile 能回答问题时可复用；证据不足、性能异常、候选改变了热点或需要验证机制时再补采。

### 3. 写出可证伪假设

主假设使用以下语义链：

1. **观察**：哪条 Run、Profile 或代码事实显示了具体问题；
2. **机制**：该问题如何造成端到端开销；
3. **最小干预**：准备改变的一个执行机制或参数族；
4. **预期**：哪些指标应朝什么方向变化；
5. **否定条件**：什么结果说明机制不成立、收益被其他开销吞没或适用范围更窄；
6. **正确性风险**：Mask、精度、权重布局、状态、Dispatch 或 Stream 语义中最易破坏的部分；
7. **范围与回退**：假设面向哪些 Workload，失败时回到哪条已验证路径。

“某技术通常更快”不是项目事实；成熟 Backend、编译器、融合或自定义 Kernel 都需要落到本设备、本 Workload 与本实现。建议一次只激活一个主机制，备选机制保持互斥，便于最小对照解释因果。

### 4. 按证据选择一个优化层

这些层是动作空间，不是逐层打卡的成熟度阶梯。Agent 每轮可选择最有信息增益的一层，也可跳过、重复、回退或停止。

| 数字 | 优化层 | 主要决策 | 典型动作 | 典型决策信号 |
|---:|---|---|---|---|
| 1 | 设备与测量校准 | 当前设备和比较面是否可信，已有事实能否解释现象 | 刷新环境、Baseline、Solution、噪声与健康事实；归纳已有 Profile | 新设备、环境漂移、结果异常、缺少兼容事实 |
| 2 | 编译与运行时 | 框架执行方式能否降低图开销或采用更优运行路径 | Compile Mode、Graph、SDPA/Runtime 开关、缓存策略 | 小 Shape、Launch Gap、图分割或成熟运行时选项尚未验证 |
| 3 | 成熟 Kernel 与 Backend 选择 | 哪条合法实现路径最适合目标 Workload | Eager、Compiled、SDPA、已有 Fused Backend、少量路径分派 | 至少两条兼容路径，Shape 或 Backend 支持差异明确 |
| 4 | Kernel 参数 | 同一实现的设备相关参数怎样取值 | Tile、Block、Warps、Stages、Vector Width、Launch 参数 | 参数敏感性已有迹象，组合可约束，资源限制可检查 |
| 5 | 图、融合与布局 | 是否调整算子边界、中间张量和读写路径 | QKV、Bias 与激活、Residual 与 Norm、Layout、中间写回 | Profile 显示 Launch 或内存写回主导，融合边界可解释 |
| 6 | 自定义 Kernel 与专门化 | 新写 Triton/CUDA 或 Shape 专门化是否值得 | 自定义 Kernel、Shape 路径、最小 Dispatcher 与显式 Fallback | 成熟路线收益停滞、热点集中，潜在收益覆盖实现和维护风险 |

常见症状与候选方向如下。它们用于提出实验，不替代 Profile 或正式结果。

| 观测症状 | 优先核对 | 可优先尝试 | 保守回退 |
|---|---|---|---|
| Attention 占比最高 | 绝对时间、序列长度、Mask、已有 Backend | SDPA/Backend 选择、等价 Attention Fusion | 原生正确 Attention 路径 |
| Projection 或前馈层占比高 | GEMM Shape、Dtype、Tensor Core、Layout、中间写回 | Compile、布局、等价 QKV 或 Bias 与激活融合 | 原始 Linear 与激活路径 |
| Norm、Residual 或小算子占比高 | Kernel 数量、Launch Gap、显存读写 | 图融合、Residual 与 Norm 等价融合 | 未融合路径 |
| 小 Shape 且 Launch-bound | Kernel 时长、GPU 空隙、图分割 | 编译、减少小算子和中间张量 | Eager 路径 |
| Memory-bound | 带宽、读写次数、访问连续性 | Layout、Coalescing、减少中间写回 | 原始布局 |
| 不同 Shape 的赢家不同 | 各 Shape 的重复正式结果、分派成本 | 少量候选和最小 Dispatcher | 通用 Fallback |
| 成熟 Backend 收益停滞 | 热点集中度、资源限制、可改机制 | Triton/CUDA 深度定制 | 已验证成熟 Backend |

### 5. 在隔离区准备并冻结候选

候选从明确的父源码身份派生，Draft 保持与正式 `solution/` 相同的相对入口和完整可执行源码闭包。Agent 或开发者只在 Draft 中修改，检查 Diff、导入边界、构建配置与明显的接口风险后，再冻结为新 Candidate。

冻结动作分配候选身份并计算源码树 Hash；`candidate.json` 只描述不可变身份、父源码、入口、创建信息和必要构建字段。假设、Verdict、运行结果和是否采用不写进候选身份。源码或已解析执行配置变化时生成新候选，旧候选保持可重放。

正式 Runner 以冻结 Candidate 为测量目标。针对可变 Draft 的快速运行可以辅助诊断，但不进入正式比较。Candidate 的本地模块、Kernel 和依赖闭包一并冻结，避免入口看似相同而实际读取外部可变文件。

本步骤区分三种“最好”：

| 名称 | 含义 | 本步骤中的作用 |
|---|---|---|
| 搜索领先项 | 单次参数搜索批次内暂时最好的配置或候选 | 帮助决定 Finalist，不代表正式采用 |
| 测量最佳项 | 相同 Comparison Key 下，由健康正式 Run 推导的最佳 Variant | 可写成可重建视图，不跨设备或协议比较 |
| 正式 Solution | 用户选择并由发布流程受控物化的主线实现；已有证据覆盖决定可声明范围 | 本步骤只读，不因局部结果自动改变 |

### 6. 完成首个端到端候选实验

对冻结 Candidate 运行目标语义组合的 Correctness 与代表性 Workload 的正式双侧 Benchmark。Run 保存两侧原始样本、Median、Speedup、健康状态、实际路径、源码与协议身份；比较结论按事先确定数量的健康正式 Run 汇总，不跨 Run 拼接样本。

准备作为主要机制主张时，增加一组最低成本、最有区分力的 Control 与 Treatment：尽量只改变该机制，并保持 Comparison Key 一致。最终 Baseline 与最终 Candidate 的总体差异不能自动归因到某一机制。必要时补一组 Before/After Profile，用来确认热点是否按预期移动；Profile 占比变化本身仍不构成因果结论。

本轮结论可落在三种语义：

- **支持**：Correctness 通过，端到端收益在重复与噪声规则下稳定，机制相关对照方向一致；
- **混合**：部分 Shape、路径或指标支持，但收益不稳定、范围较窄或副作用明显；
- **否定**：机制预期没有出现、端到端收益落在噪声内、出现可信回退，或正确性风险无法合理收敛。

否定与混合结果会改变候选优先级，同样是有效输出。它们可以引导修订、切换优化层或停止分支，不包装成性能成功。

### 7. 按需使用有限参数搜索

参数敏感性已有证据、合法组合可枚举且预计墙钟在预算内时，可把有限搜索作为候选生成器。配置很少时，逐个冻结并正式测量通常更直接；配置较多时采用统一快速筛选，再把少量 Finalist 送入正式端到端验证。本步骤的搜索只服务代表性 Workload 上的首个候选与机制判断；跨全部官方 Workload 的参数收敛、最佳视图重建和采用建议由下一步骤统一处理。

搜索设计建议固定：

- Base Candidate、环境、Workload 与参数 Schema；
- 参数范围、条件约束、有效组合数与去重规则；
- Seed、执行顺序、缓存和进程策略；
- 快速筛选与正式复核的测量协议；
- Finalist 数量、噪声边界内的近似并列处理；
- 最大配置数、正式测量次数、GPU 时间和总墙钟；
- 正确性失败、构建失败、显存不足、超时、收益停滞和预算耗尽时的停止原因。

固定 Driver 在单 GPU 上串行执行，每个配置保留紧凑 Correctness 和筛选摘要。快速筛选、Profiler 内部 Autotune 与 Microbenchmark 都不进入正式最佳视图；Finalist 以冻结 Candidate 身份在清洁进程中重跑完整 Correctness 与正式双侧 Benchmark。会生成不同 Python、Triton 或 CUDA 源码的配置直接进入 Draft 与 Freeze 生命周期，不以参数行绕过候选身份。

一次搜索使用一个 Search Run 保存共享配置、紧凑 Trial、Finalist 引用和停止原因；不另建 Sweep 目录、CSV、数据库或第二套结果系统。长搜索可以使用可恢复的 Partial 文件，正式视图忽略未提交 Partial。

### 8. 回写洞察并形成后续输入

Canonical Insight Card 集中维护在一个 Markdown 文件中，只保留少量会改变候选选择或最终机制叙事的洞察。普通尝试、临时想法、无意义失败和所有搜索点不转成 Card。

每张 Card 使用普通标题或“洞察 1、洞察 2”编号，包含：

| 字段 | 内容 |
|---|---|
| 状态 | 草拟、支持、混合、否定或被替代 |
| 范围 | 环境、设备、Workload、Shape、Dtype、Backend |
| 问题与价值 | 具体端到端瓶颈及其影响 |
| 观察与引用 | Profile、Run 和代码位置 |
| 假设与机制 | 改动为何可能影响瓶颈 |
| 预期与否定条件 | 指标方向及限制该结论的结果 |
| 对照 | Control 与 Treatment 的 Candidate 引用 |
| 正式证据 | Correctness、Benchmark 与必要 Profile 引用 |
| 新意边界 | 项目特有机制、组合或适配；成熟技术如实标为工程选择 |
| 结论、范围与回退 | 支持程度、反例、适用边界和安全路径 |

Card 只保存短解释、方向和引用，不复制原始延迟、Median、Speedup、Profile Counter 或终端输出。数字继续以 Runner-owned Run/Profile 为真值。后续全量验证可以扩展范围、反例与 Fallback；发布步骤再选择实际进入报告和演示的 Card。

## 4. 决策信号

| 观察结果 | 建议动作 | 证据语义 |
|---|---|---|
| Correctness 失败 | 定位 Mask、精度、权重布局、状态、Dispatch 或 Stream 问题；修订或放弃候选 | 失败 Run；性能数据仅诊断 |
| 端到端收益落在噪声范围 | 检查 Profile 预期是否出现；缩小改动、换层或结束分支 | 混合或否定，不声明加速 |
| Microbenchmark 变快但完整 Forward 无收益 | 估算融合外开销、数据搬运、同步与 Dispatch 成本 | 局部优化成立，项目收益未成立 |
| 代表性 Workload 稳定提升 | 保留冻结候选和正式对照，交给全量 Workload 验证 | 候选证据包，不等于正式采用 |
| 部分 Shape 提升、部分 Shape 回退 | 更新适用范围，评估通用 Fallback 或最小 Dispatcher 的价值 | 混合结论，避免跨 Shape 平均掩盖问题 |
| Profile 显示热点转移 | 更新假设并选择下一信息增益最高的层 | 原机制可能成立，但新的端到端限制已出现 |
| 参数搜索出现近似并列 | 对近似并列项使用完整正式复核，优先低风险、低复杂度方案 | Screening 只用于筛选 |
| 多个候选无有效收益或预算收敛 | 保留最后一个正确、可重放、风险清楚的候选或已验证路径，记录停止理由 | 诚实的未验证到加速结论 |

## 5. 本步骤完成信号

本步骤以“一条可信候选闭环完成”为核心，而不是强制得到正向加速。建议交给下一步骤的内容包括：

1. 一个明确的代表性 Workload 与完整比较身份；
2. 一条有实际 Profile/Run 引用的主假设及其否定条件；
3. 至少一个可重放的冻结 Candidate；
4. Candidate 的 Correctness 和正式端到端 Benchmark Run；
5. 准备主张机制时的一组最小正式对照，以及必要的 Before/After Profile；
6. 更新为支持、混合或否定的 Insight Card；
7. 对后续全量验证的建议：保留候选、继续修订、切换层、评估 Dispatcher/Fallback，或停止该路线；
8. 可选的搜索 Finalist 与可重建测量最佳视图；两者都不代表正式采用。

若本轮没有发现可信提升，交付正确候选、否定证据、范围边界和停止理由即可。后续开发可以选择低风险已验证路径继续全量正确性与发布准备，不需要制造性能或创新结论。

## 6. 本步骤文件落点

完整目标文件树见 [00_开发步骤总览](00_开发步骤总览.md)。本步骤只涉及以下路径：

| 路径 | 本步骤用途 |
|---|---|
| `solution/` | 作为候选父源码和正式实现对照；本步骤不自动写入 |
| `candidates/_drafts/<draft_id>/solution/**` | 可修改的隔离实验源码闭包 |
| `candidates/<candidate_id>/candidate.json` | 冻结候选的不可变身份 |
| `candidates/<candidate_id>/solution/**` | 冻结候选的完整可执行源码闭包 |
| `runner/` | 复用单一入口执行 Profile、Candidate Correctness、正式 Benchmark、比较与可选有限 Search；不建设第二套测量系统 |
| `results/runs/<run_id>.json` | Profile、Correctness、Benchmark 与可选 Search 的结构化记录 |
| `results/artifacts/<run_id>/` | 按需保存 Trace、Profiler 报告和有诊断价值的失败日志 |
| `results/current_best.json` | 可选的测量最佳派生视图；可由兼容正式 Run 重建 |
| `tests/test_regressions.py` | 真实缺陷值得长期防止时增加聚焦回归；不预建无来源案例 |
| `docs/04_调优证据/Insight_Cards.md` | 单一机制解释与证据引用层；出现首个真实主假设时创建 |

不创建独立 Profile 数据库、Sweep 目录、第二套 Candidate Registry、每张 Card 单独文件或手工维护的性能结果表。

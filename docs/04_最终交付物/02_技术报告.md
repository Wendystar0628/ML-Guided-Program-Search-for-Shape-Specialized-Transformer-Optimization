# 面向异构 Shape 的 Transformer GPU 优化技术报告

> 本文是当前阶段的最终技术报告底稿。所有性能数字来自仓库中的
> [RTX 4080 最终结果](../../results/final/nvidia_geforce_rtx_4080.json)；运行方式见
> [README](../../README.md)。AI 工具、模型、Skills 与代表性交互单独整理在
> [03_AI协作说明.md](./03_AI协作说明.md)，本文不重复展开。

## 摘要

同一个 Transformer 实现无法同时适配十四种差异巨大的 Shape：小 Shape
主要受 Kernel Launch 和框架调度影响，宽维度 Shape 更依赖 Tensor Core
吞吐，大 Batch Shape 会放大 Residual 与 LayerNorm 的访存成本，长序列
Attention 需要避免完整中间矩阵，而 Shape 14 首先是显存容量问题。

本项目把优化问题建模为“硬件与 Shape 感知的离线测量和确定性路由”：先探测
真实设备，再对 Workload 进行瓶颈分类，为每个 Shape 生成少量有理论依据的候选，
通过正确性和真实 GPU 计时筛选赢家，最后把路线固化为运行时表查找。项目同时实现了
两个窄而有力的自定义 Triton Kernel：Shape 6 的混合精度
Residual-plus-LayerNorm，以及 Shape 13 的 Online Softmax 因果 Attention。

在披露的 NVIDIA GeForce RTX 4080 环境上，Shapes 1–13 全部通过正确性检查，
相对给定 Baseline 的等权几何平均加速比为 **8.505368951x**。Shape 14 通过独立的
流式路径完成完整逻辑 Batch，Target median 为 **16.236815 s**，峰值 PyTorch
设备分配为 **7.307 GiB**。

必须明确三个边界：

1. **8.505368951x 是项目等权 Geomean，不是官方总分。**
2. **本文 MFU 均为 project-estimated MFU，不是官方 MFU 或官方分数。**
3. **Shape 14 是 provisional、Target-only 结果，没有 Baseline 或 Speedup。**

## 1. 问题定义与核心洞察

### 1.1 优化对象

任务要求保持给定 Transformer 的输入输出语义，并优化完整多层 Forward，而不是只展示
孤立微型算子的吞吐。输入、输出和参考计算为 FP32；内部可以使用更低精度、编译器、
CUDA Graph、Triton 或其他实现，只要最终输出通过 Comparator。

真正困难之处不是找到一个“最快 Attention”，而是理解每种 Shape 的主导成本：

| Workload 类型 | 主要现象 | 本项目的应对方式 |
| --- | --- | --- |
| 小算量、固定 Shape | GPU 未被填满，Launch 和 Python/ATen 调度占比高 | 完整 Forward CUDA Graph，配合局部 Residual-Norm Fusion |
| 窄维度或小 Head | 通用算子形态碎片化，单个 Kernel 很短 | 固定执行计划的完整 Forward 编译 |
| 宽维度、较高算术强度 | GEMM 吞吐成为主线 | 精度校验后的 FP16 Core 与库 GEMM |
| 超大 Batch | Residual、类型转换和 Norm 流量反复放大 | Batch Tiling 与双精度流 Triton Fusion |
| 较长序列 Attention | Score/Probability 中间量和 Softmax 成本突出 | Shape 专用分块 Online Softmax Attention |
| 极长序列 Shape 14 | 稠密 `S×S` Attention 和完整 Batch 无法驻留 16 GiB 显存 | 内存高效 SDPA 与逻辑 Batch 流式调度 |

### 1.2 最关键的 Problem Insight

本项目没有把低 MFU 统一解释为“Kernel 不够快”。对于很小的 Shape，低 MFU 是算量不足
和 Launch 主导的自然结果，重写大型 GEMM 不会直接解决问题；对于 Shape 6，重点是
消除跨分支 Residual/Norm 的重复流量；对于 Shape 13，重点才转向 Attention 算法边界；
对于 Shape 14，任何性能讨论都必须先建立能在有限显存中完成正确计算的执行方式。

因此，优化单元不是一个固定 Kernel，而是一个由 Attention、Linear 精度、
Residual-Norm 和外层 Runtime 组成的执行策略。不同 Shape 复用同一套测量与路由框架，
但不被迫使用同一种执行组合。

## 3. 官方合同与测量口径

### 3.1 正确性合同

Shapes 1–13 使用相同权重和输入比较 Baseline 与 Solution。Comparator 的逐元素规则是：

`abs(target - reference) <= 0.002`

或

`abs(target - reference) / abs(reference) <= 0.02`

两项是逻辑 **OR**，不能写成 `atol + rtol × |reference|`。每个 resident Shape 进行
5 次带种子的正确性测试；任何一次失败，或者请求的专用策略发生静默回退，都不能作为
该策略的正式成绩。

### 3.2 本项目 Formal 计时协议

- 编译、首次运行和初始化不计入正式计时；
- 20 次 Warmup；
- 每轮 100 次完整 Transformer Forward；
- 3 轮交替测量 Baseline 与 Solution；
- 使用 CUDA Event 记录完整 Forward；
- 主要性能统计为 Median，同时保留 P90；
- 每个专用策略记录实际执行路径，避免把 Fallback 误报为优化成功。

这是项目用于稳定比较的 Formal 协议；官方尚未公布的最终权重或总分公式不由本项目推断。

### 3.3 指标定义

| 指标 | 定义与用途 | 边界 |
| --- | --- | --- |
| Speedup | Baseline median / Target median | 仅用于 Baseline 可运行的 Shapes 1–13 |
| Achieved TFLOP/s | 项目定义的有效矩阵乘 FLOPs / Target 时间 | 不包括 Norm、激活、Mask 和转换等全部算术 |
| Project-estimated MFU | 按实际数据类型匹配本机 GEMM Anchor 后估算的理想计算时间 / Target 时间 | **工程诊断指标，不是官方分数** |
| Peak GiB | PyTorch CUDA Allocator 报告的目标路径峰值分配 | 不是整个进程或显卡物理显存占用 |
| Logical Traffic | 当前算子边界上的逻辑字节估计 | 不是硬件计数器测得的 DRAM 带宽 |

## 4. 系统架构与优化闭环

项目把热路径和测量控制面分开，避免将实验逻辑堆进 Transformer Forward。

| 层次 | 职责 |
| --- | --- |
| 官方合同层 | 保存给定计算语义、十四个 Shape 和官方源码身份 |
| Solution 数据面 | Packed QKV、Attention Backend、Linear 精度、Residual-Norm、Graph/Compile 和自定义 Kernel |
| 测量控制面 | Hardware Probe、Workload 分析、候选资格、Comparator、CUDA 计时和实际路径验证 |
| 部署层 | Formal Winner 晋升、已验证硬件 Bundle 和确定性 Dispatcher |

完整流程如下：

1. **Probe：**读取 GPU 架构、显存、软件版本和实测性能 Anchor。
2. **Analyze：**根据 Token 数、维度、Head Geometry、Attention 规模、Launch 压力和
   Fusion 机会分析 Workload。
3. **Rank：**从统一 Policy Registry 中生成最多三个符合硬件与 Shape Guard 的候选。
4. **Measure：**串行运行正确性、Smoke 和 Formal GPU 测试。
5. **Promote：**只有通过 Comparator、实际路径验证和完整 Formal 复测的赢家才能写入
   该硬件的精确路由。
6. **Dispatch：**正式运行只做表查找，不在线搜索、不重复 Profile；无法匹配已验证路由时
   使用可移植的 `eager-sdpa` 控制路径。

一个不可变 Execution Plan 同时提供给 Forward 和执行路径说明，Attention、Norm、Mask、
Graph 与 Compile 只解析一次。这样可以防止“说明使用了专用 Kernel，但实际已经 Fallback”
的控制面漂移。

Shape 14 不进入 Shapes 1–13 的 resident 路由表。它使用独立流式执行器，在 GPU 上筛选
内存安全的 Attention Policy 和 Microbatch Divisor，然后覆盖完整逻辑 `B=32` Workload。

## 5. 策略与项目自研贡献

### 5.1 实测策略分配

| 策略组合 | 最终服务的 Shape | 设计理由 |
| --- | --- | --- |
| 完整 Graph + Fused Residual/LayerNorm | 02、03、04、12 | 极小固定 Shape 以减少 Launch/调度为主 |
| Graph + FP16 Core + Efficient Attention + Compiled Norm | 01、05、09、10 | 同时降低调度和分支计算成本 |
| 固定计划 Compiled Forward + FP16 Core + Efficient Attention | 07、08、11 | 完整 Forward 编译比显式 Graph 组合更适合这些几何形态 |
| Batch-tiled Graph + FP16 Core + 自研 Triton Mixed Residual-Norm | 06 | 控制超大 Batch 的驻留量并融合高频 Residual/Norm 边界 |
| Compiled Forward + FP16 Core + 自研 Shape 13 Triton Attention | 13 | 对 `S=1024, head_dim=32` 使用分块 Online Softmax |
| Streamed FP16 Core + cuDNN SDPA | 14 | 在 16 GiB GPU 上避免稠密 Attention 并流式覆盖逻辑 Batch |

### 5.2 Shape 6：Mixed Residual-plus-LayerNorm

Shape 6 的 `B=10000` 使 Residual、Branch 输出和 LayerNorm 的反复读写成为显著成本。
自研 Triton Kernel 在一个边界内完成：

- 读取 FP32 Residual 和 FP16 Branch Update；
- 在 FP32 中进行 Residual Add、Mean、Variance 和归一化；
- 保留新的 FP32 Residual Stream；
- 中间层直接输出 FP16 Normalized Stream 供下一分支使用；
- 最终边界恢复 FP32 输出。

它与 `tile_B=128` 的 Batch-tiled CUDA Graph 组合，而不是试图捕获完整 `B=10000`
Graph。Kernel 只对实测的 width-128 推理形态开放，不伪装成通用 LayerNorm 实现。

### 5.3 Shape 13：Online Softmax Causal Attention

Shape 13 使用 `B=64, H=4, S=1024, head_dim=32`。自研 Triton Kernel 分块执行 QK
和 PV，在 FP32 中维护每行的最大值、归一化和与 Accumulator，不物化完整 Score 或
Probability Matrix。它作为专用 Attention Core 嵌入固定计划的完整 Forward 编译中。

该路径严格 Guard 为 Causal、无额外 Token Mask、Forward-only、FP16 和精确 Shape 13
几何形态；其他 Shape 继续使用经过实测的 PyTorch Efficient SDPA 或 cuDNN SDPA。

### 5.4 创新点

项目的创新不是简单包装一个现成 Attention Library，而是：

1. 把设备事实、理论瓶颈分类和真实 GPU 反馈连成可执行的逐 Shape 路由闭环；
2. 让每个优化策略显式组合 Attention、Linear 精度、Residual-Norm 与 Outer Runtime，
   同时保持单一事实源和可检查的实际执行证据；
3. 对 Shape 6 和 Shape 13 的真实瓶颈实现窄而明确的自定义 Triton Kernel；
4. 对无法 resident 执行的 Shape 14 建立独立流式协议，而不是跳过、伪造 Baseline，
   或把容量问题塞进普通路由。

## 7. Shape 14：独立流式 Target-only 结果

Shape 14 为 `B=32, S=100000, D=1024, H=16, Layers=2`。完整稠密 Attention
矩阵无法在 16 GiB GPU 上构造，完整 Batch 的输入、输出和中间状态也不适合同时驻留。

最终流式策略为 `mixed-fp16-core-cudnn`：

| 指标 | 结果 |
| --- | ---: |
| Target median | 16,236.815 ms |
| Target P90 | 16,240.448 ms |
| 完整主机端时间 | 18,182.579 ms |
| Achieved TFLOP/s | 85.6858 |
| Project-estimated MFU | 91.7134% |
| Peak device allocation | 7.307 GiB |
| Timing schedule | Microbatch 2 × 16 |

正确性路径用一个完整 `B=1, S=100000, D=1024` 长序列样本，对内部 Query-block
Reference 比较 102,400,000 个元素；本次 Trial 为 0 个失败元素，最大绝对误差
`0.000833869`。随后流式调度覆盖全部 32 个样本的逻辑 Workload。

**证据边界：该结果是 provisional、Target-only。** 当前只有一次内部长序列参考验证，
没有可执行的稠密 Baseline 延迟，因此不报告 Shape 14 Speedup，也不把它并入 Shapes 1–13
的 Geomean。

## 8. 正确性与执行完整性

项目把正确性作为硬门槛，而不是可以与性能交换的软分数：

- Baseline 与 Solution 使用相同权重和输入；
- Resident 候选通过五次 Comparator 后才能进入正式性能比较；
- Attention Backend、Linear Dtype、Residual-Norm Backend 和 Runtime Wrapper 都要与
  实际观察路径一致；
- 不满足 Shape、Dtype、Mask、设备或运行时 Guard 时，专用 Kernel 显式拒绝，而不是
  静默冒充成功；
- 路由 Bundle 绑定当前硬件、软件环境、Workload、Solution 和 Formal Protocol，
  代码或环境变化后需要重新校准。

内部 `safe` Policy 只保留参考计算顺序，用于诊断，不参与正式路由；`eager-sdpa` 是未命中
精确验证路由时的可移植控制路径。

   口径；Logical Traffic 也不是硬件 DRAM Counter。
4. **Shape 14 是 provisional、Target-only。** 当前没有 Baseline、Speedup 或正式官方
   全 Shape Reference 证据，不能并入 Resident Geomean。
5. Peak GiB 是 PyTorch Allocator 的峰值分配，不是整个进程或显卡物理显存占用。
6. 当前正确性证据覆盖已记录的 FP32 输入输出、Causal、无 Padding 变体；不同 Mask、
   Padding、Scale、Dtype 或训练/Autograd 需要独立验证。
7. Shape 6 和 Shape 13 的自定义 Triton Kernel 都是窄 Shape Specialization，不宣称通用。
8. **项目内 Hardware-aware Agent Runtime 尚未实现。** 当前完成的是可供未来 Agent 调用的
   确定性 Probe、测量、校准和路由底座，不能把 Agent 规划文档作为已完成贡献。

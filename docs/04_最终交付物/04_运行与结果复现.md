# 运行与结果复现

本文给出面向评委和复核者的最短运行路径。它不复制 Runner 的内部设计；命令、依赖和结果文件均直接指向仓库中的真实实现。

| 项目 | 当前记录 |

| 操作系统 | Windows 11，WDDM |
| CPU | Intel Core i7-14700KF，20 Cores / 28 Threads |
| 内存 | 63.83 GiB |
| GPU | NVIDIA GeForce RTX 4080，Ada，Compute Capability 8.9，16 GiB VRAM |
| 驱动 | 610.88 |
| Python | 3.12.5 |
| PyTorch / CUDA | PyTorch 2.12.1+cu132 / CUDA 13.2 |

当前数值只在上述硬件和软件栈上完成正式验证。其他设备可以使用项目保留的 Probe 与 Calibration 流程，但不应直接套用 RTX 4080 的性能结论。

## 2. 环境安装

在仓库根目录打开 PowerShell：

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-windows-rtx4080.txt
. .\activate_windows_rtx4080.ps1
.\.venv\Scripts\python.exe environment_check.py --check-extension
```

RTX 4080 环境使用 [requirements-windows-rtx4080.txt](../../requirements-windows-rtx4080.txt)。完整锁定版本记录在 [requirements-windows-rtx4080-lock.txt](../../requirements-windows-rtx4080-lock.txt)。

环境检查应确认：

- CUDA Device 可见；
- PyTorch CUDA Build 可用；
- Triton Extension 可以编译和加载；
- 当前设备不是 CPU Fallback。

## 3. 三分钟检查路径

先查看已发布的机器结果：

- [RTX 4080 最终结果 JSON](../../results/final/nvidia_geforce_rtx_4080.json)
- [RTX 4080 已验证硬件说明](../../verified_hardware/nvidia_geforce_rtx_4080/README.md)

然后运行 Resident Smoke：

```powershell
.\.venv\Scripts\python.exe verified_hardware/nvidia_geforce_rtx_4080/run_verified.py `
  --scope resident --preset smoke
```

该入口使用已固化的 Shapes 1–13 精确路由，检查模型可以加载、策略实际命中、输出正确性和 GPU 计时链路是否成立。Smoke 用于快速演示，不替代正式性能数据。

独立检查 Shape 14：

```powershell
.\.venv\Scripts\python.exe verified_hardware/nvidia_geforce_rtx_4080/run_verified.py `
  --scope streamed --preset smoke
```

Shape 14 使用独立流式执行，不进入 Shapes 1–13 的几何平均值和精确路由表。

## 4. 正式复测

正式复测 Shapes 1–13：

```powershell
.\.venv\Scripts\python.exe verified_hardware/nvidia_geforce_rtx_4080/run_verified.py `
  --scope resident --preset formal
```

正式复测 Shape 14：

```powershell
.\.venv\Scripts\python.exe verified_hardware/nvidia_geforce_rtx_4080/run_verified.py `
  --scope streamed --preset formal
```

顺序执行两个范围：

```powershell
.\.venv\Scripts\python.exe verified_hardware/nvidia_geforce_rtx_4080/run_verified.py `
  --scope all --preset formal
```

Formal 运行会更新对应硬件的最终结果区段。不同后台负载、温度、功耗状态和驱动调度可能产生小幅波动；对比时应使用相同环境和完整协议，而不是挑选单次最低值。

## 6. 测量与正确性口径

Shapes 1–13 的 Formal 协议为：

- 外部输入、参考输出和候选输出均为 FP32 语义；
- 每个 Shape 运行 5 次正确性试验；
- 20 次 Warmup、每轮 100 次完整 Forward、共 3 轮；
- 使用 CUDA Event 记录完整 Transformer Forward；
- 主要统计量为 Median 与 P90；
- Baseline 与 Solution 使用相同权重和输入；
- 编译、Graph Capture 和首次初始化不进入正式计时。

逐元素正确性条件为：

```text
absolute_error <= 0.002
OR
relative_error <= 0.02
```

两个容差是 OR 关系，不是相加关系。候选还需要提供实际执行路径证据；如果请求的专用 Kernel 或 Backend 静默回退，不能把该结果记作专用策略成功。

Shape 14 使用独立协议：完整 `B=1, S=100000, D=1024` 样本进行内部 Query-block Reference 比较，再以流式 Microbatch 覆盖逻辑 `B=32`。该正确性证据当前仍是 `provisional`，不能与 Shapes 1–13 的配对 Formal 结果等同。

## 9. 常见边界

- Bundle 绑定 GPU、驱动、CUDA、PyTorch、官方快照、Solution 与 Route Table；任一关键身份变化都可能需要重新校准。
- `safe` 只用于诊断，不是正式可路由性能策略。
- `eager-sdpa` 是未知设备或不匹配形态的便携回退，不代表已经对该设备完成最优校准。
- 项目不依赖外部 `flash-attn` Package；Shape 14 当前使用 PyTorch 提供的 cuDNN SDPA。
- 当前运行路径不调用 LLM。AI 协作说明见 [03_AI协作说明.md](./03_AI协作说明.md)。

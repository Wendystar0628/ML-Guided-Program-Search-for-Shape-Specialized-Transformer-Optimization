# Devpost 项目说明底稿

## 项目名称

**AI-Assisted Shape-Aware Transformer Kernel Optimizer**

中文说明：AI 辅助、面向消费级 GPU 的 Shape-aware Transformer Kernel 优化器。

## 一句话摘要

本项目先根据 Transformer Shape 与目标 GPU 的硬件信号对少量执行方案进行理论粗排，再以完整 Workload 的正确性和真实 GPU 延迟决定逐 Shape 路径，使同一套 Transformer 在 RTX 4080 上覆盖 Launch-bound、Compute-bound、Memory-traffic-bound 和超长序列场景。

## 问题

Transformer 的性能瓶颈不会随 Shape 保持不变：小 Shape 容易受 Kernel Launch 和框架调度开销限制，宽维度 Shape 更依赖 Tensor Core 与 GEMM 吞吐，大 Batch 会放大中间张量与 Residual/LayerNorm 的显存流量，而超长序列 Attention 甚至无法物化完整的 $S\times S$ 矩阵。

许多成熟优化实现首先面向 A100、H100 等数据中心 GPU。对于使用消费级 GPU 的开发者，直接采用单一通用路径既可能浪费硬件，也可能在极端 Shape 上无法运行。本项目因此把问题定义为：

> 在保持官方 Transformer 计算语义和逐元素误差门槛的前提下，如何利用 AI 辅助分析、硬件事实和真实 GPU 测量，为不同 Shape 选择可解释、可复现的执行方案？

## 解决方案

系统采用“理论缩小搜索空间，实测决定最终路径”的闭环：

1. 读取官方十四个 Shape，并采集目标 GPU 的 Launch、Transfer、GEMM 与 Attention Backend 能力；
2. 根据 Batch、Sequence Length、Hidden Dimension、Head Dimension、算术强度和显存容量，对少量符合条件的候选进行白盒粗排；
3. 在独立 GPU Worker 中先运行官方 Comparator，再测量完整 Transformer Forward；
4. 拒绝正确性失败、实际执行路径与请求策略不一致或没有净收益的候选；
5. 将实测赢家固化为该硬件与软件栈下的确定性逐 Shape 路由，正式运行时不再搜索，也不依赖 LLM；
6. 将 Shape 14 交给独立的 Memory-bounded Streamed Executor，在不构造完整 $S\times S$ Attention Matrix 的情况下覆盖完整逻辑 Batch。

## 核心创新

### 1. Shape-aware 理论粗排与真实 GPU 决胜

理论模型只负责解释瓶颈并缩小候选集合，不把启发式评分当作最终性能结论。最终路由由完整 Workload 的正确性与 GPU 实测共同决定，避免根据显卡型号或单个 Microbenchmark 直接猜测最快路径。

### 2. 把执行策略建模为可组合计划

每条策略由 Attention Backend、Linear Compute Dtype、Residual/LayerNorm 实现和外层 Runtime 组成。系统把它们解析为一次生成、不可变的 Execution Plan，使真实 Forward、路径说明、候选资格和结果记录共享同一事实源。

### 3. 针对真实瓶颈进行窄范围自主 Kernel 特化

项目没有为了展示 Kernel 数量而重写所有 GEMM，而是只在实测表明通用路径不足时增加专用实现：

- Shape 5 使用 Mixed FP16 Core、Efficient SDPA、项目自写 Triton Mixed Residual + LayerNorm、基于 Tensor Identity/Version 的 Unchanged-input Staging 与 CUDA Graph 组合；
- Shape 6 使用同一类项目自写 Triton Mixed-precision Residual + LayerNorm Kernel，并与 Batch-tiled CUDA Graph 组合；
- Shape 8 保留 FP32 主权重，并为固定计划 Compiled Forward 提供派生、非持久化的 FP16 Shadow Weights；
- Shape 13 使用项目自写的 Triton Online Causal Attention Kernel，并嵌入固定 Shape 的 Compiled Forward。

这些自主 Kernel 与 PyTorch、cuBLAS、cuDNN 等 Library Primitive 明确分开披露。

### 4. Shape 14 的独立执行机制

Shape 14 为 `B=32, S=100000, D=1024, H=16, Layers=2`。系统把“单样本 Attention 的二次方中间量”和“完整 Batch 无法同时驻留”视为两个不同问题：内存高效 Attention 解决前者，动态 Microbatch Streaming 解决后者。项目在目标 GPU 上联合筛选符合显存约束的 Policy 与 Microbatch，而不是把一个固定分块参数写死为通用答案。

## 主要技术路线

- **Reference contract**：保持官方构造参数、权重、`forward(x, valid_token_mask)` 接口、输出 Shape 和 FP32 外部比较语义；
- **Correctness first**：使用 `rtol=0.02`、`atol=0.002` 的逐元素 OR 条件；Resident Shape 每个运行 5 次 Seeded Trial；
- **Hardware-aware analysis**：测量 Launch、Transfer、FP16/BF16/FP32 GEMM 和 Backend Availability，并结合 Shape 特征判断主要瓶颈；
- **Bounded candidates**：只比较与该 Shape 和设备能力匹配的少量 Policy，避免无边界搜索；
- **Execution composition**：使用 Eager SDPA、Mixed-precision Core、CUDA Graph、Batch-tiled CUDA Graph、`torch.compile` 和自主 Triton Kernel 的有界组合；
- **Observed-path validation**：确认请求的 Backend 或 Kernel 确实执行，防止 Silent Fallback 被误报为优化成功；
- **Deterministic deployment**：离线校准后发布精确路由；运行时不进行 Benchmark，不调用外部 AI API；
- **Compact results**：每张已验证 GPU 只保留一份最终机器可读结果，中间实验与最终成绩分离。

## 主要结果

验证环境为 Windows 11、NVIDIA GeForce RTX 4080 16 GiB、Python 3.12、PyTorch 2.12.1 + CUDA 13.2、cuDNN 9.20.0 和 Triton 3.7.1。

| 范围 | 正确性与性能结果 |
| --- | --- |
| Shape 1–13 | 13/13 通过官方 Comparator；相对官方 Baseline 的无权重几何平均加速为 **9.192×**，逐 Shape 加速范围为 **2.334×–36.685×**；所有 Trial 的失败元素为 0，最大绝对误差为 **0.00180167**。 |
| Shape 5 | **0.501760 ms，4.710×**；使用 Mixed FP16 Core + Efficient SDPA + 项目自写 Triton Mixed Residual/LayerNorm + Version-aware Unchanged-input CUDA Graph Staging。 |
| Shape 6 | **45.323263 ms，10.730×**；使用 Batch-tiled CUDA Graph 与项目自写 Triton Mixed Residual + LayerNorm Kernel。 |
| Shape 8 | **6.147072 ms，2.334×**；FP32 参数保持权威，Compiled Forward 使用派生、非持久化 FP16 Shadow Weights。 |
| Shape 13 | **3.202560 ms，36.685×**；使用带项目自写 Triton Online Causal Attention 的固定 Shape Compiled Forward。 |
| Shape 14 | 完整逻辑 Workload 的 Target Median 为 **17.207 s**，Host-streamed End-to-end 为 **18.880 s**，PyTorch CUDA Allocator 报告的峰值 Device Allocation 为 **7.307 GiB**。该结果不声称相对 Dense Baseline 的 Speedup。 |

Shape 14 的 Useful Throughput 为 **80.8566 TFLOP/s**，项目内部估算 MFU 为 **91.8066%**。这两个数用于工程分析；项目估算 MFU **不是**尚未公布公式下的官方比赛得分。

最终机器可读结果位于 `results/final/nvidia_geforce_rtx_4080.json`，完整测量口径和逐 Shape 表位于 `TECHNICAL_REPORT.md`。

## 真实用户价值

本项目面向使用本地或消费级 GPU 进行固定 Shape Transformer 推理的 ML Engineer、Kernel Developer 和本地 AI 开发者，提供三项直接价值：

1. **让设备约束成为优化输入**：不假设每位开发者都拥有数据中心 GPU，而是根据目标设备的真实能力选择方案；
2. **降低试错成本**：用有理论依据的少量候选代替盲目枚举，再由可靠 GPU 数据完成取舍；
3. **覆盖容量受限场景**：Shape 14 证明序列长度 100000 的完整逻辑 Workload 可以在 16 GiB GPU 上通过内存受控方式完成。

这套方法的长期价值不是宣称一条 Kernel 适用于所有显卡，而是提供可解释、可校准的设备专用优化流程。目前只有 RTX 4080 结果经过完整验证。

## Feasibility 与可复现性

- 项目提供明确的环境文件、单一 Runner 入口和 RTX 4080 Verified Hardware Bundle；
- 正式执行采用已经发布的确定性路由，不承担在线搜索和 LLM 调用开销；
- Specialized Policy 具有严格资格判断，无法执行时不会冒充成功路径；
- Shapes 1–13 使用完整 Baseline/Solution Paired Measurement；Shape 14 使用独立 Target-only Streamed Protocol，避免制造不可执行的 Dense Baseline 证据；
- 结果同时绑定 Workload、官方 Benchmark Snapshot、Solution、Route Table、Runtime 和测量协议，便于判断结果是否仍适用于当前代码。

## 贡献边界

### 项目自行完成

- Shape 分析、Workload 分区和白盒候选粗排；
- Policy Composition、不可变 Execution Plan 和精确 Dispatch；
- Hardware Probe、完整 GPU 测量、Observed-path Check 和自动 Route Promotion；
- Shape 14 的 Streamed Scheduling 与动态 Microbatch 选择；
- Shapes 5/6 Triton Mixed Residual + LayerNorm Kernel、Shape 5 Version-aware Graph Input Staging，以及 Shape 8 非持久化 FP16 Shadow Weights；
- Shape 13 Triton Online Causal Attention Kernel；
- Correctness、结果合同和 Verified Hardware Artifact。

### 官方或 Library 提供

- 官方 Transformer、Baseline 和 Comparator 定义参考计算；
- PyTorch、ATen/cuBLAS、Efficient SDPA、cuDNN SDPA、CUDA Graph 和 `torch.compile` 提供底层 Library Primitive；
- 项目对这些能力进行 Shape-aware 组合和实测选择，但不把它们的 Kernel 声称为项目自研。

### AI 协作边界

Codex 协助分析、提出候选、修改实现和解释测试结果；正确性比较、路径确认、CUDA Event 测量和 Route 发布由确定性程序完成。项目内 Hardware-aware Agent Runtime 尚未实现，也不作为本次成果声明。

## 局限

- Shape 14 当前为成功运行的 **Provisional、Target-only** 结果；没有可执行的完整 Dense Baseline，因此不报告 Speedup，最终仍需接入官方 Golden Output；
- 目前只有披露的软件栈上的 RTX 4080 完成完整验证；跨硬件 Probe 与 Calibration 机制得到保留，但尚不能声称在其他 GPU 上获得相同收益；
- Useful TFLOP/s、Logical Traffic 和项目估算 MFU 是项目工程指标，不等于官方评分公式或实测 DRAM Counter；
- cuDNN、SDPA、`torch.compile` 和 Triton 的可用性依赖平台，未满足资格的专用路径需要退回 Portable Policy；
- 当前优化面向固定、已公布 Shape，不宣称能直接泛化到任意 Transformer 架构和动态输入。

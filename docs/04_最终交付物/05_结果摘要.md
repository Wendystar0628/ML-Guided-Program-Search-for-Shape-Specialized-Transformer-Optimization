## 3. Shape 14 独立结果

Shape 14 为 `B=32, D=1024, H=16, S=100000, Layers=2`。完整 Dense Attention Matrix 和完整 Resident Batch 无法在 16 GiB GPU 上成立，因此它使用独立的流式执行与内存高效 Attention。

| 指标 | 当前结果 |
| --- | ---: |
| 实际策略 | `mixed-fp16-core-cudnn` |
| Timing Schedule | Microbatch `2 × 16` |
| Target Median / P90 | 16.236815 s / 16.240448 s |
| Host End-to-End | 18.182579 s |
| Useful Throughput | 85.6858 TFLOP/s |
| 项目估算 MFU | 91.7134% |
| 峰值 Device Allocation | 7.307 GiB |
| 内部完整样本比较 | `B=1, S=100000, D=1024`，共 102,400,000 个元素 |
| 正确性 | 0 个失败元素，最大绝对误差 0.000833869 |

该结果必须同时保留以下边界：

- `provisional`：正确性来自一次内部 Query-block Reference，而不是与 Shapes 1–13 相同的五次配对 Formal；
- `Target-only`：当前没有可执行的完整 Dense Baseline，因此不报告 Speedup；
- Shape 14 不进入 Resident 几何平均，也不发布成普通精确路由；
- Attention Kernel 来自 PyTorch cuDNN SDPA，项目贡献是流式 Batch、显存守卫、Policy/Microbatch 筛选、完整调度和结果证据，不把 cuDNN Kernel 归为自研。

## 4. 方法与结果的对应关系

### 4.1 Launch-bound 小型 Shape

Shapes 2、3、4、12 的算量不足以持续占满 GPU。完整 CUDA Graph 消除重复 Launch 和 Python 调度开销，局部融合 Residual 与 LayerNorm。低 MFU 在这里主要反映 Shape 太小，不意味着应该重写大型 GEMM。

### 4.2 中型固定 Shape

Shapes 1、5、9、10 同时需要减少 Launch 开销和分支计算成本，因此使用 CUDA Graph、Mixed FP16 Core、Efficient Attention 与 Compiled Norm 的组合。

### 4.3 高 Batch Shape 6

`B=10000` 使完整驻留 Graph 不合理，也放大 Residual、Normalization 和 Dtype Conversion 的流量。项目以 Batch Tile 128 执行，并使用自定义 Triton Kernel 融合 FP32 Residual、FP16 Branch Update 和 LayerNorm。

### 4.4 窄 Head、宽维度与长序列

- Shapes 7 和 11 的 `head_dim=8` 使用固定执行计划的完整 Compiled Forward；
- Shape 8 的宽维度 GEMM 已达到较高 Useful Throughput，保留库矩阵乘并优化外围执行；
- Shape 13 使用自定义 Triton Online Causal Attention，分块完成 QK/PV 并维持 FP32 Online-softmax 状态，避免完整 Score/Probability Matrix。

### 4.5 极端容量 Shape 14

Shape 14 首先是容量问题，其次才是单 Kernel 选择问题。流式 Logical Batch 与 Memory-efficient Attention 分别解决 Batch 驻留和 `S²` 中间张量问题。

## 5. 指标解释

| 指标 | 含义 | 不代表什么 |
| --- | --- | --- |
| Median | 正式重复样本的中位延迟 | 不是最小偶然值 |
| P90 | 90% 样本不超过的延迟 | 不是官方单独评分项 |
| Speedup | Baseline Median / Target Median | Shape 14 没有该指标 |
| Useful TFLOP/s | 项目定义的有效矩阵乘 FLOPs / Target Time | 不含所有框架与非矩阵算子工作 |
| 项目估算 MFU | 依据本机 Dtype-matched GEMM Anchor 估算的计算利用率 | **不是官方总分，也不是厂商峰值利用率** |
| Peak GiB | PyTorch Peak Device Allocation | 不是整张显卡所有进程的总显存占用 |
| Logical Traffic | 当前算子边界的逻辑读写估计 | 不是 Profiler 实测 DRAM Bandwidth |

## 7. 证据边界

- 所有性能数值只对当前 Windows 11、RTX 4080、Driver 610.88、PyTorch 2.12.1+cu132、CUDA 13.2 软件栈成立。
- 跨硬件 Probe 与 Calibration 已实现，但没有第二张 GPU 的性能验证，不能表述为跨硬件普遍加速。
- 几何平均为项目使用的等权汇总；官方 MFU 权重和带宽修正尚未公布。
- PyTorch、cuBLAS/cuBLASLt、cuDNN、Efficient SDPA、CUDA Graph、`torch.compile` 与 Triton 编译器均是第三方能力。
- 项目自研重点是 Shape-aware 测量路由、执行计划、校准与发布流程、Shape 6 Triton Mixed Residual-Norm、Shape 13 Triton Online Causal Attention，以及 Shape 14 流式调度。

# 持续优化与自主改进方法论

> 适用仓库版本：`main@d1b2e66`  
> 本文用于指导 Codex 持续运行优化脚本、阅读搜索证据并改进项目。它规定思考方式与判断标准，不规定具体行动路线。

## 一、把项目视为序贯科学实验，而不是不断追加代码的工程项目

当前系统已经具备程序空间生成、Branch-local TPE、Successive Halving、分级测量、配对晋升、历史证据复用、Shape 隔离和部署闭环。Codex 的首要职责不再是扩张框架，而是持续回答：

\[
\text{下一单位 GPU 时间，怎样最大化发现真实可部署性能提升的概率？}
\]

对任一假设 \(h\)，优先级应近似取决于：

\[
V(h)
=
\frac{
P(h\text{ 为真}\mid D)
\cdot
\Delta T_{\text{upper}}(h)
}{
C_{\text{experiment}}(h)
}
\]

其中 \(D\) 是已有观测，\(\Delta T_{\text{upper}}\) 是对完整 Forward 的潜在收益上限，\(C\) 是验证成本。优先研究“高概率、高上限、低验证成本”的假设，而不是结构最复杂或最有新意的假设。

## 二、每次运行都应更新认知，而不只是更新配置

持续优化应形成：

\[
\text{观测}
\rightarrow
\text{机制假设}
\rightarrow
\text{可证伪预测}
\rightarrow
\text{区分性实验}
\rightarrow
\text{更新认知}
\]

Codex 不应只报告“谁更快”，还应判断“为什么更快”以及“什么证据会否定当前解释”。

历史数据只能作为先验，不能作为事实本身。旧结果、低保真结果和相邻 Shape 结果都应影响搜索方向，但不得阻止新信息产生。没有找到更优配置，只在搜索覆盖、测量功效和候选表达能力都足够时，才构成“接近上限”的证据。

### 搜索历史的复用与失效

搜索历史应遵循“能证明兼容就复用，不能证明兼容就重新测量”的原则：

- 硬件、官方 Shape、执行实现和测量协议均未改变时，继续复用 `search.sqlite3` 中的 Screen Trial、TPE 分布、Enhanced 缓存和重复探索记录；文档、脚本、预算或搜索调度的变化不应清空有效证据。
- Kernel、Transformer 执行路径、依赖运行时或测量协议变化后，旧延迟和晋升结论不再作为当前性能事实；由新的 Evidence Identity 建立独立 Study。
- 已失效历史中的优秀 Config 和 Branch 仍可作为低优先级 Warm Start，但必须在新实现上重新通过正确性与性能测量，不能直接部署。
- 不因证据失效删除数据库。旧记录保留用于回顾结构规律，新旧数值不得混合排序或计算收益。
- Resident Shapes 与 Shape 14 分别使用 `observations/search/resident` 和 `observations/search/shape14`，只在各自 Scope 内复用历史，避免把完全不同的执行机制互相迁移。

因此，代码更新后的默认处理不是“全部沿用”或“全部清空”，而是保留历史文件、隔离不兼容数值、复用仍有意义的结构，并在当前代码上重新确认赢家。

## 三、按失效层级诊断，而不是把所有问题归因于搜索算法

当优化停滞时，依次区分以下层级：

| 层级 | 核心问题 |
|---|---|
| 程序表示 | 真正更优的等价程序是否能被当前 `ConfigSpec` 和基础积木表达？ |
| 候选生成 | 在可表达空间内，TPE 是否产生了有信息量的新点？ |
| 预算分配 | Successive Halving 是否让有潜力的结构获得了足够证据？ |
| 测量 | SCREEN、ENHANCED、FORMAL 是否在估计同一个性能事实，噪声是否掩盖差异？ |
| 晋升 | 真正稳定的收益是否有足够统计功效被接受？ |
| 执行 | 被测路径是否确实执行了请求的程序，而非发生隐藏回退？ |
| 部署 | 被批准的程序是否在完全相同环境与 Shape 上被实际调用？ |

只有定位层级后，改动才有意义。不要用“换一种优化器”掩盖程序空间不足，也不要用“增加 Kernel”掩盖测量失真。

## 四、冲突判断采用多智能体并行分析

当日志、测量结果、Profiler、代码机制或不同 Shape 的表现相互矛盾时，不进行冗长的证据分级和口头置信度打分。直接派出多个相互独立的 Agent，从不同维度并行分析同一组原始记录。

建议至少覆盖以下视角：

- 测量与统计：检查采样协议、配对关系、噪声、热状态和缓存状态；
- 搜索与优化：检查搜索覆盖、候选生成、历史偏置、预算分配和过早淘汰；
- GPU 执行与性能模型：检查计算、带宽、Launch、布局、融合和资源占用；
- 语义与实现：检查正确性、实际执行路径、隐藏回退和配置是否真正生效。

各 Agent 应独立给出机制解释、因果链和能够区分竞争解释的可证伪预测。主 Agent 不按投票数机械取多数结论，而是比较各解释对现有观测的覆盖能力、内部一致性和可验证性，最终输出：共同结论、关键分歧、最可能原因以及仍需由后续运行判定的问题。

Resident Shapes 与 Shape 14 应分别分析。前者主要关注驻留执行、融合、布局和 Launch；后者主要关注流式分块、I/O 复杂度与逻辑批调度，二者的经验不得无条件互相迁移。

## 五、所有性能判断必须回到完整 Forward 的上限

对局部优化，先使用 Amdahl 定律判断整体上限：

\[
S_{\text{total}}
\le
\frac{1}{(1-f)+f/s}
\]

其中 \(f\) 是目标部分占完整 Forward 的比例，\(s\) 是局部加速倍数。若整体上限低于测量噪声或比赛价值，继续优化该局部没有意义。

再用 Roofline 与 I/O 思维判断机制：

\[
P
\le
\min(P_{\text{peak}}, BW\cdot I)
\]

Codex 应区分：

- 计算受限；
- 带宽受限；
- Kernel Launch 受限；
- Layout/Cast 物化受限；
- 编译、Graph 或 Host 调度受限。

每个性能假设至少应给出：

- 预期消除的 FLOP、字节、Launch 或同步；
- 对完整 Forward 的收益上限；
- 预期在哪些 Shape 上成立；
- 若结果不成立，说明原性能模型中哪一项错误。

## 六、用“简单遗憾”评价搜索，而不是用 Trial 数评价搜索

搜索的目标不是让 Optuna 产生更多 Trial，而是降低：

\[
r_t
=
\min_{x\in D_t}L(x)-L(x^\star)
\]

实际无法知道 \(L(x^\star)\)，因此应用以下替代问题判断搜索质量：

- 固定 GPU 时间内，最佳可行 ENHANCED 延迟是否继续下降？
- 找到可通过 FORMAL 的 Challenger 所需时间是否缩短？
- 新点是否覆盖此前没有证据的结构或局部区域？
- SCREEN 对 ENHANCED 的排序是否具有稳定相关性？
- 被淘汰结构是因为充分证据，还是因为预算、噪声或历史偏置？
- 多轮没有部署更新时，是接近物理上限，还是搜索系统已经停止获取新信息？

“搜索空间仍有大量未测点”不等于“值得继续均匀搜索”；“连续多轮没有赢家”也不等于“当前实现已最优”。

## 七、Codex 的每次分析应保持五个要素

每轮监控结束后，分析应至少包含：

1. **事实**：本轮实际发生了什么，不混入解释；
2. **主假设**：最可能的机制是什么；
3. **竞争解释**：还有哪些原因能产生相同观测；
4. **可证伪预测**：主假设为真时，后续证据应呈现什么特征；
5. **置信度与上限**：判断有多确定，值得投入的最大资源是多少。

不要直接从异常日志跳到代码修改，也不要把单次最快值解释为稳定性能规律。

## 八、反对过度工程化的判定规则

只有满足下列至少一项，才值得增加新的模块、抽象或指标：

- 扩大了当前无法表达的等价程序空间；
- 明显降低 GPU 测量成本；
- 消除了系统性搜索偏差；
- 提高了性能判断的统计可信度；
- 使一次失败能够被准确归因；
- 直接缩短搜索到可部署赢家的时间。

以下内容不应被视为进展：

- 更多日志但没有新的决策能力；
- 更多指标但没有明确用途；
- 更多搜索算法但没有等预算对照；
- 更多抽象层但没有降低复杂度或开销；
- 更多 Kernel 名称但没有新的计算或数据流机制；
- 更长运行时间但没有新信息。

## 九、项目真正的进展定义

持续优化中的有效进展只有四类：

1. 部署了经过正式统计验证的更快程序；
2. 在同等预算下更快发现可部署 Challenger；
3. 通过区分性实验排除了一个重要错误假设；
4. 扩展了具有明确性能机制的程序表达能力。

Codex 应始终围绕这四类结果组织推理。项目的目标不是让搜索系统越来越复杂，而是让它越来越接近一个可靠的自动科学过程：以最少 GPU 时间，发现、解释并验证真正的性能提升。

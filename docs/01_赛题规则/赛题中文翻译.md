## 3.1 背景

Transformer 是现代 AI 中广泛使用的神经网络架构，也是许多自然语言处理、计算机视觉、语音、推荐系统和大语言模型的核心结构。

Transformer 的主要思想是自注意力。自注意力允许序列中的每个 Token 与其他 Token 直接交互。与循环模型相比，Transformer 可以并行处理 Token，因此适合利用 GPU 加速。

给定矩阵形式的输入序列：

$$
X \in \mathbb{R}^{N \times d}
$$

其中 $N$ 是序列长度，$d$ 是隐藏维度。Transformer 首先把输入投影为 Query、Key 和 Value 矩阵：

$$
Q=XW_Q
$$

$$
K=XW_K
$$

$$
V=XW_V
$$

Scaled Dot-Product Attention 的计算方式为：

$$
\operatorname{Attention}(Q,K,V)
=\operatorname{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V
$$

其中 $d_k$ 是每个 Attention Head 的维度。缩放因子 $\sqrt{d_k}$ 用于防止点积值过大，从而避免 Softmax 分布不稳定。

Transformer 的计算开销较高，重要操作包括矩阵乘法、Attention Score 计算、Softmax、Normalization 和 Feed-Forward Layer。这些操作可能受 GPU 计算吞吐、显存带宽、Cache 效率、Kernel Launch 开销和 Tensor Core 利用率限制。

本赛题要求参赛者使用 AI 辅助方法，优化给定 GPU 上 Transformer 结构的运行效率。优化后的实现应在相对参考实现保持数值正确的前提下提高性能。

可考虑的优化方式包括 Operator Fusion、Memory Layout 优化、低精度计算、Tensor Core、Softmax 优化，以及自定义 CUDA、Triton、TensorFlow 或 PyTorch 实现。

本赛题旨在探索 AI 如何帮助开发者分析 Transformer Workload、定位瓶颈，并为特定 GPU 硬件生成更高效的实现。

## 3.2 问题陈述

- 官方给出固定的 Transformer Layer 公式。参赛者需要提交一个或多个实现这些 Layer 的 GPU Kernel，并通过给定测试用例。
- 测试用例使用 PyTorch 或 TensorFlow 编写。参赛者可以按需修改 Layer 实现，也可以自行决定哪些部分应融合为一个 Kernel。
- 测试会比较参赛实现与原始 PyTorch/TensorFlow 实现的输出差异。赛题正文给出的门槛为相对误差 `< 0.02` 或绝对误差 `< 0.002`；当前官方 PyTorch Benchmark 的实际逐元素判断见“官方 PyTorch Benchmark 的可执行口径”。
- 测试输入包含不同 Shape，例如大/小 Batch Size、大/小 Sequence Length 和大/小 Dimension。所有 Shape 组合会向参赛者公开，参赛者可以在 Layer 实现中加入 Shape 检查，为不同 Shape 选择不同实现。
- 鼓励使用 AI 工具，以便参赛者在有限时间内为不同输入 Shape 实现不同 Kernel。
- 在参赛者自己的机器上优化并测试代码。不同硬件可以采用不同优化方法。
- 提供清晰的技术报告，并详细说明使用的 AI Skills/Tools，可获得额外评价。

## 4. 官方 PyTorch Benchmark 的可执行口径

本节记录当前用户提供的官方 PyTorch Benchmark 实际执行的内容。它是 Reference 和本地 Benchmark 工具，不等同于尚未公布的最终 MFU 评分公式。

### 4.1 Transformer 参考计算

当前脚本的参考模型执行：

1. Pre-Norm Multi-Head Self-Attention；
2. Q、K、V 和 Attention Output 分别使用带 Bias 的 `nn.Linear`；
3. Attention Score 为缩放后的 $QK^T$；
4. `causal=True` 时屏蔽未来位置；存在 `valid_token_mask` 时屏蔽无效 Key；
5. Softmax 使用 FP32 计算，再转回输入 Dtype；
6. 无效 Query 位置的 Attention Output 置零；
7. Attention Residual 后执行第二个 Pre-Norm；
8. FFN 使用两层带 Bias 的 `nn.Linear` 和 `approximate="none"` 的 Exact GELU；
9. 每层结束后把无效 Token 位置置零；
10. 重复指定 Layer 数，最后执行 `nn.LayerNorm`，并再次把无效 Token 位置置零。

`forward(x, valid_token_mask)` 的输出 Shape 必须为 `[batch_size, seq_len, d_model]`。参赛实现需要保持该调用接口，并保持参数名兼容，或相应修改 Weight Copy 逻辑。

### 4.2 当前脚本的正确性比较

当前脚本对每个输出元素计算：

$$
e_{abs}=|y_{candidate}-y_{reference}|
$$

该元素需要是有限值，并满足以下两个条件之一：

$$
e_{abs}\leq \texttt{atol}
\quad\mathbf{OR}\quad
e_{abs}\leq \texttt{rtol}\cdot|y_{reference}|
$$

当前命令行默认值为 `rtol=0.02`、`atol=0.002`。所有输出元素都通过时，该次 Accuracy Trial 才通过；脚本默认运行 5 次 Trial。

这是一项逐元素 **OR** 条件。脚本没有使用 `torch.isclose` 的 `atol + rtol * abs(reference)` 加法条件。赛题正文写作 `<`，当前脚本实现为 `<=`；执行复现时应明确使用了哪个官方脚本版本。

### 4.3 当前脚本的本地计时行为

- 随机数据生成不计入模型延迟，Baseline 与 Candidate 使用固定输入；
- Baseline 与 Candidate 分别 Warmup；
- CUDA 使用当前 Stream 上的 `torch.cuda.Event` 测量，并在采样前后同步；
- 多轮测试交替 Baseline 与 Candidate 的测量顺序；
- 输出 Mean、Median、P90、Minimum、Token/s；
- 脚本中的 Speedup 使用 `baseline_median / candidate_median`；
- 当前命令行默认 `warmup=20`、`repeats=100`、`benchmark_rounds=3`。

这些是当前脚本的默认行为，不代表官方已经确定最终提交成绩必须使用同一统计协议。

### 5.2 Shape 与正确性

- Appendix 的十四行是实际 Test Shapes；官方脚本中的默认 Shape 只是 Demo。每个 Appendix Shape 可以单独运行。
- 每个 Shape 都需要通过正确性检查后才会计入性能评价。讲者没有明确说明单个 Shape 失败只使该 Shape 得零分，还是会影响整个 Technical Execution。
- 说明会明确的外部数值语义是 FP32：Baseline 和精度检查使用 FP32。内部允许量化或混合精度计算，只要输入输出比较通过精度门槛。
- 讲者确认最新版 PyTorch 脚本的门槛与赛题文字一致；当前脚本把它实现为 `rtol=0.02`、`atol=0.002` 的逐元素 OR 条件。
- 输入 Scale 被回答为固定，但会议转写没有可靠记录最终测试值。Padding Ratio 和 Token Mask Pattern 的问题没有得到清楚回答。

### 5.3 Shape 14

- Shape 14 属于正式测试范围，不能依赖完整稠密 Attention Matrix 在常规设备上驻留。
- 讲者明确建议把计算拆分为多个 Block，逐块完成计算。
- 分块、流式或 Memory-efficient Attention 都可以作为实现方式，但会议没有指定唯一算法；最终仍以官方计算语义和输出精度检查为准。
- 讲者表示会提供用于比较的输入输出对，但没有明确其发布日期、文件格式和读取协议。

### 5.4 编译、Warmup 与性能评分

- 编译时间和第一次运行可以从正式性能测量中排除。
- 讲者表示通常会进行约 20 次 Warmup。这是说明会中的口头惯例，不是完整的最终计时协议。
- 讲者口头表示可以使用非默认 Flag，只要正确性通过；但没有明确 Baseline 与参赛实现是否需要使用对称的编译设置。
- 讲者多次表示，Technical Execution 的性能部分倾向由各 Shape 的 MFU 加权组合，并考虑设备带宽以改善跨硬件公平性。
- MFU 权重、FLOPs 口径、峰值分母、带宽修正和不同硬件间的标准化方式尚未公布，因此当前不能据此计算或宣称“官方总分”。
- 讲者更关注正确性通过后的最终 Kernel 性能，而不是 AI 用多短时间生成实现。

# 评测规则与技术口径

> [返回会议总览](./00_会议内容总览.md)。本文只整理会议披露的评测与实现边界；最新版官方文字和可执行 Benchmark 仍是最终事实源。

## 1. 任务与硬件定位

### 官方明确

- 目标是在自己的机器上实现和优化 Transformer Layer，使其在该设备上运行得更快。
- 可以使用消费级 GPU、Apple 芯片、数据中心 GPU 或云端设备；讲者更鼓励针对自己的设备进行优化。
- 如果拥有多种设备，可以选择其中一种作为最终重点优化和报告的平台。
- 评委不会把所有方案搬到同一张 GPU 上重新运行，因为设备专用优化本身就是赛题意图的一部分。
- 技术报告需要披露操作系统、设备、GPU、显存或 HBM 等运行环境，并说明如何达到最佳结果。

### 边界

“自己的机器”是明确偏好，不是对云端或数据中心 GPU 的禁令。设备示例也不是硬件白名单。

## 2. Workload 与正确性

### 官方明确

- Appendix 中发布的十四行是实际 Test Shapes，默认脚本中的 Shape 只是演示。
- 每个 Appendix Shape 可以独立运行，并需要通过正确性检查。
- PyTorch 和 TensorFlow Benchmark 表达相同的计算，选择其中一个框架实现即可。
- Baseline 与精度检查使用 FP32。讲者明确允许内部量化，并表示只关心输入输出精度；FP16、TF32 等具体内部策略属于对此口径的工程理解，仍需以最终 Comparator 通过为准。
- 最新 PyTorch 脚本口头确认使用 `rtol=0.02`、`atol=0.002`；具体比较语义以最新版脚本为准。
- 可以使用 Python、Triton、CUDA 或更低层语言。跨语言实现可以保存输入输出，再与参考结果比较。

### 尚未确认

- Padding Ratio 和 Token Mask Pattern 在问答中没有得到清楚回答，不能从转写内容推导最终 Mask 规则。
- 讲者说某个 Shape 精度失败会得到零分，但没有明确零分只作用于该 Shape，还是影响整个 Technical Execution。
- 输入 Scale 被回答为固定，但转写没有可靠记录具体数值，应读取最新版 Benchmark。

## 3. Shape 14 的含义

Shape 14 为 `B=32, D=1024, H=16, S=100000, Layers=2, FFN=1024`。讲者明确承认完整稠密 Attention Matrix 对大多数设备不可行，并建议把计算拆成多个 Block 逐块完成。官方还表示会提供输入输出对用于比较，但具体发布时间和文件形式没有确定。

由此可以确定：

- Shape 14 属于正式测试范围，不能因 Dense Baseline 不可运行而永久跳过。
- 官方明确接受并建议分块计算。

以下属于项目判断，而非官方限定的唯一算法：

- 流式 Attention、Online Softmax 等是可评估的实现候选，而非官方指定算法。
- 不物化完整 `S×S` Score 或 Probability Tensor。
- 同时考虑 Attention 方向和 Batch/输入输出驻留的分块，避免只切 Query 后仍超出显存。
- 官方输入输出对发布后，为无法运行 Dense Baseline 的 Shape 建立独立正确性路径。
- 本项目仍以保持官方 Transformer 语义为默认边界；任何近似或稀疏化方案都不能被预先视为合规，最终至少需要通过官方精度检查。

## 4. 计时口径

### 官方明确

- 编译时间可以不计入正式性能。
- 第一次运行可以排除。

### 口头惯例，尚非完整协议

- 讲者表示通常会 Warmup 约 20 次。
- 正式 Repeat 次数、统计量、异常值处理和是否固定其他命令行参数没有完整公布。
- 讲者口头表示可以使用非默认 Flags，只要通过精度检查；但没有说明参赛实现和 Baseline 是否必须使用对称编译设置。

因此，项目可以继续使用清晰的 Warmup、CUDA Event、Median 和 P90 作为内部协议，但不能把这些自有设置写成官方唯一评分协议。

## 5. Technical Execution 的性能方向

讲者多次表示，正确性通过后，性能部分倾向使用各 Shape 的 MFU 加权组合，并可能把设备带宽纳入公平性考虑。讲者也明确表示，更关注最终 Kernel 达到的性能，而不是 Agent 用多短时间生成代码。

以下内容仍未定稿：

- 每个 Shape 的权重；
- MFU 的准确 FLOPs 口径和峰值分母；
- 带宽如何进入评分；
- 不同硬件之间的标准化方式；
- 失败 Shape、性能异常值和分数上限的处理。

项目当前应保存逐 Shape 原始数据，并准备：

- 正确性结果；
- Solution 延迟；仅对 Baseline 可执行的 Shape 同时保留 Baseline 延迟与 Speedup；
- 算法 FLOPs 口径；
- Achieved FLOP/s；
- 明确说明峰值分母的项目估算 MFU；
- 对 Memory-bound、Launch-bound 和 Compute-bound Shape 的最小解释。

在官方公式公布前，不自行计算或宣称“官方总分”。Speedup 仍是有用的工程指标，但不应是最终技术成绩的唯一表达。

## 6. 五项评分标准

| 评分项 | 权重 | 本次材料明确展示的关注点 |
| --- | ---: | --- |
| Technical Execution | 35% | 扎实工程基础、结构清晰的代码、经过思考的架构、有效使用 API 或模型、可靠运行的 Demo，以及体现有意识且有能力决策的技术复杂度 |
| Innovation & Problem Insight | 20% | 思路与方法的原创性；问题理解是否清晰、尖锐；是否说明挑战为何重要以及方案如何直接回应 |
| Impact & Relevance | 20% | 对真实用户或相关方有可触及、可感知的价值，影响不局限于完成黑客松题目 |
| Feasibility & Practicality | 15% | 方案可真实构建并超越原型；资源使用适度；架构能在现实条件下成立；实现有依据 |
| Presentation & Communication | 10% | 仅 Final Event 评分；表达清楚，故事从问题到方案再到潜力连贯，答问体现真实理解 |

## 7. 开源实现与自主贡献

会议明确允许使用开源 AI 工具和 LLM，并把 FlashAttention、KernelAgent 作为参考案例；但没有给出“可直接复用任意现成 Kernel 实现”的宽泛许可。讲者还特别提醒，数据中心 GPU 上已有大量成熟项目，参赛者需要体现对自己 Solver 和设备的实际优化。

因此：

- 使用 PyTorch、Triton、CUDA、编译器和公开算法思想与会议口径相容；直接复用成熟 Kernel 到什么程度仍应如实披露，并突出本项目自己的实现与优化贡献。
- FlashAttention 不是指定实现，KernelAgent 也不是必选框架。
- 仅包装现成库而无法解释自身贡献，可能削弱 Technical Execution 与 Innovation 的说服力。
- 自主贡献应来自真实瓶颈，例如设备专用分块、Fusion、布局、参数选择或可解释的 Shape 路由，而不是为了形式重写已经接近上限的算子。

## 8. 仍需等待官方确认的事项

1. MFU 权重、计算公式与带宽修正。
2. Shape 失败的具体计分范围。
3. Padding、Token Mask 和输入 Scale 的最终可执行定义。
4. 正式 Warmup、Repeat 与统计协议。
5. Shape 14 输入输出对的发布日期、格式和读取方式。
6. 截止时间 `2026-09-01 12:00` 的时区。

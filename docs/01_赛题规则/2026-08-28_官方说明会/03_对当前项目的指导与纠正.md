# 对当前项目的指导与纠正

> [返回会议总览](./00_会议内容总览.md)。本文是基于会议口径对当前设计的工程判断，不代表官方逐字要求；实现细节和证据边界以当前 Runner 与 GPU 结果为准。

## 1. 总体判断

当前项目不需要推翻重来。它的核心洞察——不同 Shape 和硬件会暴露不同瓶颈，因此先建立硬件画像，再用理论模型粗排少量候选，最后以真实 GPU 结果固化逐 Shape 路由——与会议方向高度一致。

比赛主线覆盖 Shape 14、逐 Shape 原始性能指标和真实 AI 协作材料。跨硬件扩展继续保留，自研 Agent Runtime 推迟到性能主线稳定后；自主 Kernel 是否投入由真实剩余性能空间决定，而不是为了形式固定增加。

## 2. 与会议方向一致的现有设计

| 当前设计 | 会议带来的判断 |
| --- | --- |
| RTX 4080 作为主要验证设备 | 符合优化自己设备、选择单一最终 GPU 的定位 |
| Hardware Probe 与设备画像 | 能向 AI 和路由器提供显存、带宽、能力与性能事实 |
| Shape-aware 候选与精确路由 | 符合每个 Appendix Shape 独立运行、瓶颈不同的现实 |
| Top 候选后进行真实 GPU 实测 | 理论只负责缩小空间，实测决定赢家，方向正确 |
| Correctness → Smoke → Formal → Promotion | 是对官方“测试、Profile、继续迭代”方向的项目化实现，不是官方指定流程 |
| FP32 外部语义、内部混合精度 | 会议明确允许，只需继续通过最新版 Comparator |
| PyTorch 单框架路线 | 已经足够，无需增加 TensorFlow 平行实现 |
| 将编译和首次运行排除在正式计时之外 | 与会议口径一致；CUDA Graph Capture 和具体 Warmup 边界仍属于项目测量协议 |

## 3. 必须纠正的设计

### 3.1 Shape 14 使用独立的流式执行计划

Shape 14 已进入项目交付范围，但使用独立 `benchmark-streamed`，不混入 Shape 1–13 的普通 Paired Sweep，也不强行运行不可驻留的 Dense Baseline：

1. 独立入口使用 `batch_streamed`，固定以 `B=1` 检查单样本语义，再由显存守卫和 GPU 短测选择能够整除 32 的 Timing Microbatch；
2. 每个样本使用不物化完整 `S×S` Score/Probability Matrix 的内存高效 Attention；
3. cuDNN 与 Efficient Attention 分别通过完整样本 Comparator 和短测，由本设备实测选择赢家；
4. 完整逻辑 Batch 记录 GPU Latency、Host-to-Device/Compute/Device-to-Host 时间、峰值显存、Useful FLOPs 和 Achieved FLOP/s；
5. 当前正确性使用完整 `B=1` 的 Query-block Reference，明确标记为 `provisional`；接入官方 Golden Output 后再升级为正式正确性与路由证据。

Batch Streaming 解决完整 Batch 驻留，内存高效 Attention 解决单样本的二次方中间量；两者是正交问题，也分别位于 Runner 调度层和 Attention 实现层。

### 3.2 结果中心从 Speedup 扩展到原始性能事实

Median、P90 和 Speedup 继续服务工程调优，但最终展示还需要逐 Shape：

- 正确性；
- Solution 延迟；仅在 Baseline 可执行时报告 Baseline 延迟和 Speedup；
- FLOPs 口径；
- Achieved FLOP/s；
- 峰值算力假设与项目估算 MFU；
- 显存占用，以及必要时的带宽或 Roofline 解释；
- 实际命中的策略或 Kernel。

官方权重、MFU 分母和带宽修正尚未公布，因此不写死一个“官方评分器”。结构化结果先保存 Useful FLOPs、Latency、Achieved FLOP/s 与峰值显存，公式明确后再组合即可。

### 3.3 将自主 Kernel 作为高优先级评分增强项

Packed QKV、PyTorch SDPA、CUDA Graph 和 `torch.compile` 是有效的工程优化，也可以继续作为已验证赢家。风险在于，如果最终只有成熟后端编排，评委可能难以区分项目自己的 Kernel 技术贡献。

自写 Triton/CUDA Kernel 不是会议明确列出的硬门槛。最自然的评分补强也不是重写所有 GEMM，而是先选择确实远离理论上限、现有库又无法直接处理的问题：

- 先使用最简洁的 Batch Streaming 与当前运行栈内存高效 Attention，让 Shape 14 正确、可运行；
- 外部 FlashAttention 不作为安装依赖，只参考其内存复杂度与 Online Softmax 思路；
- 当 cuDNN/Efficient 路径在 Profile 和理论上限上都显示明确空间时，再实现项目自己的 Triton/CUDA Online Attention；
- 对其他 Shape 只在 Profile 证明有净收益空间时增加 Triton/CUDA Fusion；
- 保留现有高性能路径，并通过路由隔离新候选的风险；
- 清楚区分借鉴的算法思想、使用的库能力和项目自行实现的部分。

### 3.4 Agent 目标需要重新排序

会议要求真实使用并解释 AI 工具，不要求先完成一个自研 Agent 产品。当前合理顺序是：

1. 让现有确定性 Runner 继续承担正确性、测量和路由发布；
2. 用实际 Codex 协作完成 Shape 14、性能分析和 Kernel 迭代；
3. 整理真实使用的工具、模型、Skills 和代表性交互；
4. 性能主线稳定后，再开发项目内 Agent，使其复用同一 Runner 完成诊断与下一轮规划。

专用 Agent 仍然有价值，但它的比赛价值必须来自对 Kernel 结果的真实增益，而不是 CLI、上下文压缩或工具数量本身。

### 3.5 跨硬件能力退居扩展价值

会议允许只提交一张 GPU 的结果。因此：

- RTX 4080 应成为 Technical Execution 的正式数据锚点；
- 已验证硬件 Bundle 继续承担精确复现；
- 新设备 Probe、粗排和校准说明方法具有扩展潜力；
- 未在其他硬件实测前，不把跨硬件路由描述成已经验证的普遍性能结论。

这不会削弱长期架构，反而使比赛主张更可信：本机结果是事实，跨设备能力是可执行的扩展机制。

### 3.6 提交证据从“最后整理”变成最小正式产物

评委不会统一复跑代码，使报告和展示成为理解结果的主要入口。需要的不是新建庞大结果数据库，而是准备少量清晰产物：

- 一条最短运行命令；
- 精确环境与测量协议；
- 逐 Shape 正确性、Solution Latency、MFU 和策略；对 Baseline 可执行的 Shape 再给出 Speedup；
- 3–5 个脱敏的 AI 协作案例；
- 实际工具、模型和 Skills 清单；
- 一张主架构图、一张逐 Shape 结果图和少量典型瓶颈案例。

## 4. 按评分项组织项目贡献

| 评分项 | 项目应优先展示的内容 | 需要避免的表达 |
| --- | --- | --- |
| Technical Execution | 全 Shape 正确性、逐 Shape MFU、自有 Kernel、真实 GPU 路径 | 只报几何平均 Speedup；把库调用说成自研 Kernel |
| Innovation & Problem Insight | Shape 与硬件瓶颈不同；理论粗排加实测决胜；Shape 14 的流式算法 | 从 Policy 名单、Hash 或 Manifest 开始讲故事 |
| Impact & Relevance | 让消费级和非数据中心设备得到设备专用优化；跨硬件可校准 | 把单张 4080 的结果外推为所有 GPU 已验证 |
| Feasibility & Practicality | 单一入口、有限候选、离线校准、在线确定性路由、资源边界 | 为展示工程感而增加复杂平台或数据库 |
| Presentation & Communication | 问题 → 瓶颈 → 方法 → 数据 → 用户价值；能解释每个关键取舍 | 堆叠内部术语，或展示大量无法快速理解的过程证明 |

## 5. 推荐后续主线

1. 继续完善 Shape 14 的 Batch-streamed 路径，并在正式 Golden Output 可用后替换 provisional Reference。
2. 建立逐 Shape Useful FLOPs、Achieved FLOP/s 和最小带宽分析，不猜官方权重与 MFU 分母。
3. 继续实测 cuDNN/Efficient 等现有内存高效路径；仅在显存、性能和理论上限给出明确理由时实现自主 Triton/CUDA Kernel。
4. 保持当前 Shape 1–13 的已验证赢家，不让新方案破坏已有路由。
5. 整理最小 Tech Report、运行入口和真实 AI 协作材料。
6. 在性能主线稳定后继续实现项目内 Hardware-aware Agent，使其调用现有确定性服务完成长期调优。

## 6. 推荐展示主线

最终叙事可以压缩为：

> 同一个 Transformer 在不同 Shape 和消费级 GPU 上会落入不同瓶颈，单一路径无法稳定获胜。系统先用 Probe 和理论模型生成少量有依据的候选，再以真实 GPU 正确性与性能决定逐 Shape 路由；极端长序列由内存高效的分块或流式路径处理，在线执行不承担搜索开销。AI 负责提出和实现候选，确定性程序负责测量与发布。

这条主线可以同时回应 Technical、Innovation、Impact、Feasibility 与 Presentation，而不需要用复杂工程名词替代核心贡献。

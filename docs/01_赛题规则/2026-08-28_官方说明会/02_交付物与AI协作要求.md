> [返回会议总览](./00_会议内容总览.md)。本文区分“实际使用 AI 完成开发”与“自行开发一个 Agent 产品”，避免把规划能力写成已完成成果。

## 1. 会议明确要求的提交内容

### Source Code

- 提交参赛者和 Agent 生成并在项目中实际使用的源码。
- README 说明依赖、编译方式和运行方式。
- 提交项目中实际使用过的 Agent Skills。

- 操作系统、设备、GPU、显存或 HBM，以及相关运行环境；

- 人类如何向 AI 提供目标、硬件信息、约束、领域知识和反馈；
- 一部分人类与 AI 工具的交互历史；
- 如何得到最佳正确性与性能结果。

## 2. AI Agent 在本赛题中的官方含义

会议描述的 AI 辅助循环是：

1. 理解 Transformer、当前实现和设备信息；
2. 检查 Kernel Launch、数据搬运、计算时间及其他性能指标；
3. 诊断瓶颈并产生更好的实现；
4. 运行正确性检查和 Benchmark；
5. 再次 Profile，根据反馈继续迭代。

会议重点强调 AI 如何真实帮助学习、实现、测试和优化 Kernel；同时，讲者明确表示最终 Kernel 性能比开发耗时更重要。现有材料没有把“自行开发 Agent Runtime”列为硬性要求或独立评分项。

幻灯片明确写明可以使用开源 AI 工具和 LLM。列举的工具和模型只是示例，不是封闭许可名单；个别名称还可能存在幻灯片拼写或自动转写误差。

## 3. 必须区分的三类对象

| 对象 | 提交时的正确表述 |
| --- | --- |
| 实际用于本项目的 Codex、其他 AI 工具与模型 | 如实记录工具、模型、提示方式、人的判断和实测反馈 |
| 未来项目内的 Hardware-aware Agent | 只有真正实现并用于调优后，才能作为已完成能力展示 |
| 规划中的 Device、Attention、Profile 等领域 Skill | 只有实际创建并使用过的 Skill 才能进入“已使用 Skills”清单 |

不能用未来 DeepSeek Agent 的设计替代真实的 Codex 协作历史，也不能把文档中的 Skill 设想写成已经使用的提交证据。

## 4. 当前架构与 Agent 的合理关系

本项目现有的确定性能力适合作为 Agent-ready 执行底座：

- Hardware Probe 采集事实；
- Shape 与硬件模型缩小候选空间；
- Runner 串行执行正确性、Smoke 和 Formal；
- 实测结果决定赢家；
- Promotion 发布精确路由；
- 结构化结果为下一轮判断提供反馈。

LLM Agent 的价值是阅读这些事实、提出瓶颈假设、生成或修改候选、决定何时 Profile 以及规划下一轮。正确性、计时、设备锁和路由发布仍应由确定性程序控制。

这套边界既能让 Agent 有足够强的项目专用能力，也不会让通用 CLI、复杂记忆系统或多 Agent 基础设施先于性能主线膨胀。

## 5. 最小且可信的 AI 协作材料

官方口头要求的是“一部分交互历史”。推荐提交 3–5 个脱敏、连续且能解释关键决策的案例，每个案例只保留：

1. Shape、硬件事实和性能现象；
2. 人类提出的目标、约束或领域判断；
3. AI 给出的瓶颈假设和候选改动；
4. 实际执行的正确性与 GPU 测量；
5. 保留、淘汰或转向的理由。

不需要倾倒全部聊天，也不应包含 API Key、私人路径、账号信息或与项目无关的对话。被删掉的失败路线可以选择一两个最能说明判断质量的案例，而不是制作庞大的过程档案。

## 6. Tech Report 的最小结构

1. 问题与设备：为何同一个 Transformer 在不同 Shape 和设备上有不同瓶颈。
2. 运行环境：OS、GPU、显存、驱动、CUDA、PyTorch、Triton 和测量协议。
3. 方法：Probe、瓶颈分类、候选生成、GPU 实测、路由与专用 Kernel。
4. 正确性：FP32 输入输出、误差阈值和逐 Shape 结果。
5. 性能：逐 Shape Latency、项目估算 MFU 和必要的带宽解释；仅在 Baseline 可执行时报告 Speedup。
6. AI 协作：工具、模型、实际 Skills、人类引导方式和代表性交互。
7. 局限：只在已披露设备上验证的结论、未确定的官方评分公式及其他边界。

## 7. 对 KernelAgent 的参考边界

会议引用的 [Meta KernelAgent](https://github.com/meta-pytorch/KernelAgent) 展示了硬件指标驱动的 Kernel 生成与优化思路。本项目可以借鉴严格路径验证、Best-so-far 和实测反馈，但没有必要照搬其全部多 Agent、Fuser 或 UI 结构。
